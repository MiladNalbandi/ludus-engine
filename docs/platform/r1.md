# R1 — the content read side

The first app, and the first routes. A game client can read published waves from the Python
service, with the caching that makes the poll cheap.

Split in two. **R1a**, here, is the read surface over a storage port, proved against an
in-memory repository. **R1b** puts PostgreSQL behind the same port and points the editor at it.
Nothing above the port changes when it does — that is what the port is for.

## Acceptance criteria

|          | Criterion                                                              | State |
| -------- | ---------------------------------------------------------------------- | ----- |
| **AC-1** | Published waves are listed in play order; a draft never appears        | green |
| **AC-2** | The `/status` hash **equals** the list ETag for the same data          | green |
| **AC-3** | `If-None-Match` is read the way clients write it, and a match is a 304 | green |
| **AC-4** | One wave, and its document as the exact stored bytes; a draft is 404   | green |
| **AC-5** | A batch returns the published documents and silently omits the rest    | green |
| **AC-6** | The active level lists only its published waves                        | green |

The six public routes, all answering the contract frozen at v1.0.0:

```
GET  /api/v1/public/status
GET  /api/v1/public/waves
GET  /api/v1/public/waves/{id}
GET  /api/v1/public/waves/{id}/raw
POST /api/v1/public/waves/batch
GET  /api/v1/public/wave-levels/active
```

## The one that matters

**AC-2 is asserted as string equality.** The poll hash and the list ETag are not two functions
that ought to agree; they are one function called twice. If they could drift, a client would be
told "changed" by one signal, refetch, and be handed a 304 validated against the other. It never
settles, and nothing in a log looks wrong.

Everything else follows from that. The catalogue hash sorts by id before hashing, because the
catalogue is a set of facts and row order is the database's business — unsorted, a query plan
change would look to every client like new content.

## Reading If-None-Match

A table, not a couple of examples, because getting this wrong fails nothing visibly. It turns
caching off for one platform's HTTP stack and the only symptom is a bill.

Accepted: `"abc"`, `W/"abc"`, bare `abc`, a comma-separated list of any of those, and `*`.
Refused, as a miss rather than an error: empty, `"unterminated`, `""`, `W/`. A header nobody can
parse must never produce a 304 — that hands the client a body it does not have.

## Apps, and what mounting an app means

`content` is the first app, and it ships inside the platform. It is read by the _same_ loader
that reads an installed plugin, from the same `manifest.toml` format, so an app that one day
leaves this repository and returns through `plugin install` is the same thing to the core.

The core still knows nothing about it. `mounting.py` imports an app by the name in its manifest
and asks for a `router`. The import is dynamic on purpose: the wall forbids the core from
_knowing_ about an app, and a loader that imports a name it was handed knows nothing. A static
`from wavemaker.apps.content import router` would be the violation, and `lint-imports` fails the
build for it.

**An installed plugin is registered, appears in `/health`, and contributes no routes.** Nothing
has put its code on the path yet — that is R5. It is written as an explicit `mountable` set
rather than left to an import that happens to fail, because "it errored, so we skipped it" is
how a plugin silently stops working.

## What changed in R0's tests

Three R0 tests asserted that no app existed. That was true when they were written and is not
true now, so they were changed rather than deleted:

- `/health` with no plugins directory now lists the built-in `content`, not an empty list. "No
  plugins configured" means no _installed_ apps.
- The skeleton test now checks that every app that ships has a `manifest.toml`, since a built-in
  without one would simply never load and nothing would say so.

## Proved against a running server, not only in tests

```
GET /health          → {"status":"ok","version":"0.1.0","apps":[{"name":"content",…}]}
GET /public/status   → {"contentHash":"e3b0c442…"}
GET /public/waves    → 200, ETag: "e3b0c442…"      ← the same string
     + If-None-Match → 304
     + W/"…"         → 304
GET /public/waves/demo_pressure → 404
```

## What R1b still owes

PostgreSQL behind `WaveRepository`, with documents stored as the exact bytes that were written
and a generated `jsonb` column beside them for queries; tenancy, so one deployment serves more
than one game; and the editor pointed at Python to prove the contract really is unchanged.
