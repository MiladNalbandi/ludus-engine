# R8, first half — the editor as a shell plus app modules

The editor is now a shell and a set of modules. The shell owns signing in, the navigation and
one catch-all route. Each module is the screen for one backend app, and the shell shows it only
when the service says that app is loaded. Light Wave Maker moved in as the `content` module
with its wave JSON format untouched.

This is the first half of #76. It defines the module interface so that a module can later
arrive from an installed plugin's `ui/` folder, but it does not load external bundles: that
needs R5 (plugin install) and is the second half, described at the end of this file.

The journey test was run against the Python service (all three tests pass) through the new
shell. CI runs it against the Java engine, which takes the "does not report its apps" path
below.

## How the shell decides what to show

```
  sign in ──▶ shell restores the session (once, for every module)
                 │
                 ├──▶ GET /api/engine/health   (plain fetch, no token)
                 │        200 {apps:[…]}      → reported: show modules whose app is listed
                 │        401 / 403 / 404     → unreported: show every built-in module
                 │        anything else       → error screen with "Try again"
                 │
                 └──▶ GET /api/v1/me           → who is signed in, and the project
```

Visibility is a pure function of the latest report. Nothing stores an "enabled" flag, so
switching an app off and reloading removes its screen, and nothing else has to be told. An app
that is loaded but has no module — `progression` today, or an installed plugin with no UI — is
listed in the rail under "Running without a screen" rather than hidden.

**Why `/health` is read without a token.** On the Python service it is open on purpose: the
app list is the only outside evidence that the loader ran. On the Java engine it is not a route,
and Spring answers 401. Sent through `apiFetch`, that 401 would trigger a refresh, a retry and
a `NotSignedIn`, and a valid session would be sent to the login page because an engine has no
app list.

**Why an engine that does not report its apps shows every module.** The Java engine has no app
registry and serves the whole v1 contract as one process. Hiding every screen from it would
leave an empty editor pointed at an engine that serves all of them. The rail says which case it
is in. A 5xx is not treated as either answer: showing every screen because the service is down
would be a guess presented as a fact.

`/health` is the one route the editor calls that is not in `docs/api/openapi-v1.json`. It is the
platform's operations route (R0, AC-6), not part of the content contract.

## The module interface

Everything the shell knows about a module is in `editor/src/shell/module.ts`:

```ts
export const MODULE_API_VERSION = 1;

type ModuleScreenProps = {
  params: Readonly<Record<string, string>>;   // decoded values of the route's :name segments
  href: (...segments: string[]) => string;    // an address inside this module, each part encoded
};

type ModuleRoute = {
  path: string;     // '' for home, 'schema', 'waves/:id' — a literal beats a named segment
  title: string;    // the document title
  screen: ComponentType<ModuleScreenProps>;
};

type EditorModule = {
  api: 1;           // the interface version it was written for
  app: string;      // the backend app, by the name /health reports
  slug: string;     // where it is mounted: /<slug>/…
  label: string;    // the name in the navigation
  summary: string;  // one line under the label
  routes: readonly ModuleRoute[];   // exactly one has path ''
};
```

It is plain data plus React components: no classes, no lifecycle hooks, no registration side
effects. A bundle can produce one by evaluating a single default export, and
`createModuleRegistry` checks it before anything renders. It refuses:

- a module written for another interface version;
- two modules for one app, or two at one slug;
- a slug the shell owns (`login`, `api`, `_next`) or one that is not a single lowercase segment;
- a module with no home screen, or two routes of the same shape.

A module never writes its own slug into a link — it asks `href` — so the shell can mount it
anywhere. It never imports from `src/shell/` beyond the types in `module.ts`. What a module may
use from the editor is `src/lib/`: `apiFetch`, the request helpers in `requests.ts` (which turn
a refusal into an error carrying the engine's own message), `useEngineCall`, and the small UI
pieces in `ui.tsx`.

Routing is done by the shell, not by files under `src/app`. Next.js has one module route,
`src/app/(shell)/[module]/[[...path]]/page.tsx`, which asks the registry for the screen. That is
what will let a module from a plugin bring screens without adding a file to this app. The old
address `/waves/:id` redirects to `/content/waves/:id`.

## What exists

| Module       | App           | Address                               | Screen                                                                      | Contract operations                                                        |
| ------------ | ------------- | ------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Content      | `content`     | `/content`                            | Catalogue: waves (publish, unpublish), levels (activate, open, new)        | `listWaves`, `publishWave`, `unpublishWave`, `listWaveLevels`, `activateWaveLevel` |
|              |               | `/content/waves/:id`                  | Light Wave Maker, unchanged                                                 | `getWaveDocument`, `replaceWave`                                           |
|              |               | `/content/levels/new`, `/levels/:id`  | Level authoring: name, description, waves in play order, delete            | `createWaveLevel`, `getWaveLevel`, `updateWaveLevel`, `deleteWaveLevel`    |
| Inventory    | `inventory`   | `/inventory`, `/inventory/items/:id`  | Item catalogue, with a form to create, edit and delete                      | `listItems`, `saveItem`, `deleteItem`                                      |
|              |               | `/inventory/schema`                   | The attribute schema, edited as stored text                                 | `getItemSchema`, `replaceItemSchema`                                       |
| Economy      | `economy`     | `/economy`, `/economy/players/:id`    | Players (paged), a player's wallet, grant currency                          | `listPlayers`, `getPlayerWalletAsAdmin`, `grantPlayerCurrency`             |
| Media        | `media`       | `/media`, `/media/sprites`            | Audio clips and sprites: list with preview, upload, delete                  | `listAudioClips`, `uploadAudioClip`, `deleteAudioClip`, `listSprites`, `uploadSprite`, `deleteSprite`, `streamAudioClip`, `streamSprite` |
| Leaderboards | `leaderboard` | `/leaderboards`, `/leaderboards/boards/:id` | Boards, standings at a chosen size, create, change and delete a board | `listLeaderboardsAsAdmin`, `getLeaderboardPageAsAdmin`, `saveLeaderboard`, `deleteLeaderboard` |

Each new screen is deliberately narrow — list, view, and the main write. Not built:
`getItem` (the list already carries every field), `getPlayer`, item grants, rewards, the XP
curve, audio mixing, API keys and app configuration.

Details that are easy to get wrong, and are pinned by tests:

- **Item attributes are JSON text inside a string**, as the contract has them. The editor sends
  the characters the author typed and never parses and re-serialises them. The item schema is
  sent and shown byte for byte, for the same reason.
- **Uploads are multipart with the file under `file`** and no hand-set `Content-Type`, which
  would carry no boundary.
- **`getLeaderboardPageAsAdmin` names only `limit`.** The Python service accepts a cursor there
  too, but the Java never did, so the screen reads the first page at a chosen size.
- **A delete answers 204**, which `apiJson` would fail to decode; the request helpers treat any
  2xx as success.
- **A level may not name a wave twice**, so "Add a wave" offers only waves not already in it.

## The project picker

The design names a project picker in the shell. The contract has no route that lists projects:
an access token is for exactly one, which `GET /api/v1/me` reports. The shell shows that
project in the rail. A picker needs a route that does not exist yet.

## What the second half must add

The "done when" of #76 is: installing a plugin with a `ui/` folder adds its screen with no
change to the shell, and removing the app removes the screen. The second half needs all of the
following.

1. **R5 first.** `wavemaker plugin install` must put a plugin's `ui/` folder somewhere the
   service can serve it. Today an installed plugin is registered and reported by `/health` but
   brings no code (`platform/plugins/mounting.py` says so).
2. **The service serves the bundle.** A route such as `GET /plugins/<app>/ui/<file>`, open like
   `/health`, serving only files under that plugin's `ui/` directory, with a JavaScript content
   type, `nosniff`, and an immutable cache keyed by the plugin version.
3. **`/health` says which apps have a UI.** Each entry needs at least
   `{"name", "version", "ui": {"entry": "/plugins/<app>/ui/module.js", "api": 1, "integrity": "sha384-…"}}`.
   `/health` is outside the frozen v1 contract, so this is a platform decision rather than a
   contract change, but it must be written down as carefully as one: the editor will depend on it.
4. **A loader in the shell.** For each reported app that has a `ui` entry and no built-in
   module, the shell fetches the entry through its own proxy (`/api/engine/plugins/…`), imports
   it as an ES module (`import(/* webpackIgnore: true */ url)`, so the bundler does not try to
   resolve it at build time), and passes the default export through `createModuleRegistry`
   together with the built-in modules. The registry is then built per report rather than once
   at module load, which today's `ShellFrame` does.
5. **One React.** A plugin bundle must not ship its own React: two copies break hooks. The
   bundle has to treat `react` and `react-dom` as externals that the shell provides — through an
   import map, or by changing the default export to a factory `(host) => EditorModule` where
   `host` carries React and the request helpers. A factory is the more explicit of the two and
   would be interface version 2; the registry already refuses a version it does not implement.
6. **What a plugin UI may touch.** A bundle runs on the editor's origin and can call `apiFetch`
   with the signed-in author's token. That is the point — it is the screen for its app — but it
   means installing a plugin is trusting its UI as much as its backend. The integrity hash from
   `/health` must be checked before the module is evaluated, the editor needs a
   Content-Security-Policy that allows scripts only from its own origin, and the install step is
   where a plugin's signature or source is judged.
7. **Isolation of failure.** A bundle that fails to load, throws while evaluating, or fails the
   registry's checks must be reported in the rail beside its app ("could not load its screen:
   …") and must not stop the other modules from rendering. Today a bad built-in module throws at
   startup, which is right for code shipped with the editor and wrong for code installed later.
   A React error boundary around each screen does the same once it has rendered.
8. **A slug collision with a built-in module.** The registry refuses it. The loader must turn
   that refusal into the per-plugin report above, keeping the built-in module.
9. **Styles.** A plugin's screens can use the shell's classes (`.screen`, `.panel`, `.data`,
   `.form-stack` and the rest in `globals.css`). Anything else must come in the bundle, scoped
   to the module, so one plugin cannot restyle another.
10. **The end-to-end proof.** A Playwright test that installs a fixture plugin with a `ui/`
    folder, sees its screen in the navigation and opens it, removes the plugin and sees the
    screen gone. It has to run against the Python service, because the Java engine has no
    plugins; the compose stack CI uses today runs the Java engine.

## How to check it

```bash
cd editor
npm ci
npm run typecheck && npm run lint && npm test && npm run verify:types
LUDUS_ENGINE_URL=http://localhost:8080 npm run build && rm -f next-env.d.ts
```

Against a running service, sign in and the rail lists the loaded apps with their versions. The
journey runs with `LUDUS_ENGINE_URL`, `LUDUS_EDITOR_URL`, `LUDUS_E2E_EMAIL` and
`LUDUS_E2E_PASSWORD` set to that stack: `npm run e2e`.
