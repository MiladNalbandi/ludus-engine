# R8 — the editor as a shell plus app modules

The editor is now a shell and a set of modules. The shell owns signing in, the navigation and
one catch-all route. Each module is the screen for one backend app, and the shell shows it only
when the service says that app is loaded. Light Wave Maker moved in as the `content` module
with its wave JSON format untouched.

#76 was done in two halves. The **first half** made the shell, the module interface and the
built-in modules. The **second half** ([below](#second-half--a-plugins-screen-arrives-with-the-plugin))
lets a module arrive from an installed plugin's `ui/` folder: install a plugin that has one and
its screen appears in the editor, with no change to the editor; remove the plugin and the screen
is gone.

## How the shell decides what to show

```
  sign in ──▶ shell restores the session (once, for every module)
                 │
                 ├──▶ GET /api/engine/health   (plain fetch, no token)
                 │        200 {apps:[…]}      → reported: show modules whose app is listed
                 │        401 / 403 / 404     → unreported: show every built-in module
                 │        anything else       → error screen with "Try again"
                 │
                 └──▶ GET /api/v1/me           → who is signed in, and the project
```

Visibility is a pure function of the latest report. Nothing stores an "enabled" flag, so
switching an app off and reloading removes its screen, and nothing else has to be told. An app
that is loaded but has no module — `progression` today, or an installed plugin with no UI — is
listed in the rail under "Running without a screen" rather than hidden.

**Why `/health` is read without a token.** On the Python service it is open on purpose: the
app list is the only outside evidence that the loader ran. On the Java engine it is not a route,
and Spring answers 401. Sent through `apiFetch`, that 401 would trigger a refresh, a retry and
a `NotSignedIn`, and a valid session would be sent to the login page because an engine has no
app list.

**Why an engine that does not report its apps shows every module.** The Java engine has no app
registry and serves the whole v1 contract as one process. Hiding every screen from it would
leave an empty editor pointed at an engine that serves all of them. The rail says which case it
is in. A 5xx is not treated as either answer: showing every screen because the service is down
would be a guess presented as a fact.

`/health` is one of the two routes the editor calls that are not in `docs/api/openapi-v1.json`;
the other is the plugin UI route of the second half. Both are platform operations routes (R0,
AC-6), outside the frozen v1 contract, which this release does not change. Their shape is
written down below as carefully as a contract would be, because the editor depends on it.

## The module interface

Everything the shell knows about a module is in `editor/src/shell/module.ts`:

```ts
export const MODULE_API_VERSION = 2;          // the first half shipped 1; see "Interface version 2"

type ModuleScreenProps = {
  params: Readonly<Record<string, string>>;   // decoded values of the route's :name segments
  href: (...segments: string[]) => string;    // an address inside this module, each part encoded
};

type ModuleRoute = {
  path: string;     // '' for home, 'schema', 'waves/:id' — a literal beats a named segment
  title: string;    // the document title
  screen: ComponentType<ModuleScreenProps>;
};

type EditorModule = {
  api: 1 | 2;       // the interface version it was written for
  app: string;      // the backend app, by the name /health reports
  slug: string;     // where it is mounted: /<slug>/…
  label: string;    // the name in the navigation
  summary: string;  // one line under the label
  routes: readonly ModuleRoute[];   // exactly one has path ''
  styles?: string;  // version 2 only: CSS, scoped by the shell to this module's screens
};
```

It is plain data plus React components: no classes, no lifecycle hooks, no registration side
effects. `createModuleRegistry` checks it before anything renders. It refuses:

- a module whose shape is wrong — a missing label, routes that are not a list, a route with no
  screen — naming the field (a plugin's module is a value no compiler saw);
- a module written for an interface version the shell does not implement (it implements 1 and 2),
  or a version 1 module carrying `styles`;
- two modules for one app, or two at one slug;
- a slug the shell owns (`login`, `api`, `_next`) or one that is not a single lowercase segment;
- a module with no home screen, or two routes of the same shape.

A module never writes its own slug into a link — it asks `href` — so the shell can mount it
anywhere. It never imports from `src/shell/` beyond the types in `module.ts`. What a module may
use from the editor is `src/lib/`: `apiFetch`, the request helpers in `requests.ts` (which turn
a refusal into an error carrying the engine's own message), `useEngineCall`, and the small UI
pieces in `ui.tsx`.

Routing is done by the shell, not by files under `src/app`. Next.js has one module route,
`src/app/(shell)/[module]/[[...path]]/page.tsx`, which asks the registry for the screen. That is
what lets a module from a plugin bring screens without adding a file to this app. The old
address `/waves/:id` redirects to `/content/waves/:id`.

|              |               | `/inventory/schema`                   | The attribute schema, edited as stored text                                 | `getItemSchema`, `replaceItemSchema`                                       |
| Economy      | `economy`     | `/economy`, `/economy/players/:id`    | Players (paged), a player's wallet, grant currency                          | `listPlayers`, `getPlayerWalletAsAdmin`, `grantPlayerCurrency`             |
| Media        | `media`       | `/media`, `/media/sprites`            | Audio clips and sprites: list with preview, upload, delete                  | `listAudioClips`, `uploadAudioClip`, `deleteAudioClip`, `listSprites`, `uploadSprite`, `deleteSprite`, `streamAudioClip`, `streamSprite` |
| Leaderboards | `leaderboard` | `/leaderboards`, `/leaderboards/boards/:id` | Boards, standings at a chosen size, create, change and delete a board | `listLeaderboardsAsAdmin`, `getLeaderboardPageAsAdmin`, `saveLeaderboard`, `deleteLeaderboard` |

Each new screen is deliberately narrow — list, view, and the main write. Not built:
`getItem` (the list already carries every field), `getPlayer`, item grants, rewards, the XP
curve, audio mixing, API keys and app configuration.

Details that are easy to get wrong, and are pinned by tests:

- **Item attributes are JSON text inside a string**, as the contract has them. The editor sends
  the characters the author typed and never parses and re-serialises them. The item schema is
  sent and shown byte for byte, for the same reason.
- **Uploads are multipart with the file under `file`** and no hand-set `Content-Type`, which
  would carry no boundary.
- **`getLeaderboardPageAsAdmin` names only `limit`.** The Python service accepts a cursor there
  too, but the Java never did, so the screen reads the first page at a chosen size.
- **A delete answers 204**, which `apiJson` would fail to decode; the request helpers treat any
  2xx as success.
- **A level may not name a wave twice**, so "Add a wave" offers only waves not already in it.

## The project picker

The design names a project picker in the shell. The contract has no route that lists projects:
an access token is for exactly one, which `GET /api/v1/me` reports. The shell shows that
project in the rail. A picker needs a route that does not exist yet.

## Second half — a plugin's screen arrives with the plugin

```
  author                          service (Python)                         editor (browser)
  ──────                          ────────────────                         ────────────────
  bulletin/                       wavemaker plugin install bulletin@1.0.0
    manifest.toml  [ui] api = 2     sha256 + Ed25519 signature checked
    __init__.py                     ui/module.js hashed FROM THE SIGNED BYTES
    ui/module.js                    plugins/bulletin/installed.json  ◀── the install record
  wavemaker plugin build
  wavemaker plugin publish        restart: GET /health                ──▶  shell reads the report
                                    {"name": "bulletin", "ui": {...}}       for each ui entry:
                                  GET /plugins/bulletin/1.0.0/ui/     ◀──   fetch via /api/engine
                                      module.js   (the disk, read-only)     hash == integrity?
                                                                              no → rail, never run
                                                                              yes → import those bytes
                                                                            factory(host) → module
                                                                            createModuleRegistry
```

Nothing in the editor or the service names the plugin. The fixture that proves it,
`service/tests/fixtures/bulletin/`, is an ordinary app folder: a manifest with `[ui]`, a backend
with one route behind an editor's token, and `ui/module.js`, one screen.

### `[ui]` in the manifest

```toml
[ui]
entry = "module.js"   # a JavaScript file directly under ui/ (the default)
api = 2               # the editor's module interface version the bundle was written for
```

Read strictly, like `[permissions]`: an unknown key, an entry with a directory part, a name that is
not `.js`/`.mjs`, or an `api` that is not a whole number is refused when the manifest is read
(`platform/kernel/ui.py`). The platform does not judge `api`; the editor does.

- **Build** refuses a `ui/` folder with no `[ui]` (a screen that would silently never appear), and
  a `[ui]` naming a file the folder does not have.
- **Install** refuses a signed package whose `[ui]` entry is not in the archive. A `ui/` folder
  with no `[ui]` still installs, because R5 packages carried one before this existed; it is
  unpacked and never served.

### The install record, and where the integrity comes from

`plugin install` writes `plugins/<name>/installed.json` into the staging directory, before the
rename that puts the plugin in place:

```json
{"format": 1, "name": "bulletin", "version": "1.0.0", "sha256": "<archive>", "key": "<key id>",
 "ui": {"entry": "module.js", "api": 2, "integrity": "sha384-<base64>"}}
```

The integrity is the SHA-384 of `ui/<entry>` **read out of the archive in memory**, after its
checksum and signature verified and before a byte is unpacked. So the bundle's hash is part of
what R5 already signs: the signature covers the archive, the archive contains the bundle, and the
record is derived from those bytes only. A package cannot forge its own record: the archive format
has no top-level `installed.json` (R5's closed list of entries), and unpacking opens every file
for exclusive creation.

A plugin copied into the plugins directory by hand has no record. Its backend still runs, as R5
decided; its `ui/` is not offered (a warning is logged), because nothing vouches for the bytes.

### `/health`, second-half shape

An installed plugin with a served screen carries `ui`. Built-in apps never do: their modules are
compiled into the editor. Every other entry is unchanged.

```json
{"status": "ok", "version": "0.1.0", "apps": [
  {"name": "bulletin", "version": "1.0.0",
   "ui": {"entry": "/plugins/bulletin/1.0.0/ui/module.js", "api": 2,
          "integrity": "sha384-…"}},
  {"name": "content", "version": "1.0.0"}
]}
```

- `entry` — an absolute path on the service, always `/plugins/<name>/<version>/ui/<file>`, each
  segment percent-encoded. The editor refuses any other shape without fetching it.
- `api` — the `[ui]` declaration's interface version.
- `integrity` — Subresource Integrity form, from the install record, never from the disk.

### The UI route

`GET /plugins/{name}/{version}/ui/{path}` (`platform/plugins/ui.py`), open like `/health` and
outside the frozen contract. It answers only for an installed plugin with a served screen, only
for its installed version, and only with a file under that plugin's `ui/` directory:

- every segment is checked as text: no empty, `.` or `..` segment, no hidden name, no backslash,
  NUL or `:`; then every component on disk is refused if it is a link; then the result must
  resolve inside `ui/`; then the file is opened with `O_NOFOLLOW` and must be a regular file;
- only `.js`/`.mjs` (`text/javascript; charset=utf-8`), `.css`, `.json`, `.map`, `.svg`, `.png`,
  `.jpg`, `.webp`, `.gif` and `.woff2` are served, each with its own type; anything else, HTML
  included, is a 404;
- every answer carries `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox; base-uri 'none'; form-action 'none';
  frame-ancestors 'none'`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy:
  no-referrer`, and `Cache-Control: public, max-age=31536000, immutable` — safe because the version
  is in the address and one version is never installed twice;
- only `GET`; a write method is a 405.

The editor's proxy forwards `x-content-type-options` and `content-security-policy` too, and the
editor's own policy is not applied to `/api/engine/*`, so a plugin file keeps the service's
policy when it passes through.

The traversal tests send the request path straight to the ASGI application (an HTTP client would
tidy `..` away first) and aim at JavaScript files planted outside `ui/` — a type the route *does*
serve — so only the path checks stand in the way. Replacing the resolver with a naive join makes
eight of them fail.

### Interface version 2

`MODULE_API_VERSION` is now 2, and the shell implements 1 and 2. Version 2 adds two things and
takes nothing away:

```ts
type ModuleHost = {                    // what the shell hands a plugin
  api: 2;
  React: typeof import('react');       // the shell's React: one copy, so hooks work
  engine: { fetch, json, send, sendJson, sendText, jsonBody, segment, Refused, NotSignedIn };
  useEngineCall, formatMoment;
  ui: { ConfirmDelete, Problems, EngineError, SubNav };
};
type ModuleFactory = (host: ModuleHost) => EditorModule;   // a bundle's default export
// and EditorModule.styles?: string
```

A plugin bundle is **one ES module with no imports** whose default export is a `ModuleFactory`.
It must be version 2 — a version 1 module is a plain object, and one shipped in a bundle would
have to bring its own React. The built-in modules are unchanged plain values; a version 1 module
is still accepted. The host is frozen, groups included, so one plugin cannot replace
`engine.fetch` for the plugins loaded after it.

### The loader (`editor/src/shell/plugins.ts`)

The shell now builds its registry from each `/health` report rather than once at import. For
every reported app with a `ui` entry and no built-in module, on its own:

1. the entry is that plugin's own UI address and the interface version is 2 — else refused,
   nothing fetched;
2. `GET /api/engine<entry>` through the editor's existing proxy; it must answer 2xx with a
   JavaScript type and at most 16 MiB;
3. the bytes are hashed with `crypto.subtle` and compared with `integrity` (strongest algorithm
   wins, as in SRI; an integrity it cannot read is a refusal, not a pass) — **a mismatch is
   reported and the bytes are never evaluated**;
4. **the same bytes** are evaluated, from a `blob:` URL, with `import(/* webpackIgnore */ …)`.
   Importing the entry's URL after checking a separate fetch would let the second answer differ;
5. the default export must be a function; it is called with the host; the module it returns must
   be version 2 and must name the app it was installed as;
6. `createModuleRegistry([...accepted, module])` — the very checks a built-in meets. A slug clash
   with a built-in is refused there and the built-in stays; of two plugins at one slug, the one
   `/health` lists first wins, whatever order the bundles arrive in;
7. its `styles` are scoped (below).

Every failure becomes `{app, version, reason}` and the rail lists it under **Screens that could
not load**, instead of under "Running without a screen". Bundles are fetched in parallel and
judged in report order. An evaluated bundle is cached by entry and integrity, so reloading the
shell does not evaluate it twice. A bad *built-in* module still throws at import, which is right
for code that ships with the editor.

Once a screen has rendered, **an error boundary** (`ScreenBoundary`) around every module screen —
built-in or not — catches a render error and shows "<label> stopped working", the message and
"Try again"; the rail and every other module keep working.

### Styles

A module's `styles` are parsed by the browser into rules, and each rule is inserted into one
`@scope ([data-module="<slug>"])` block — every screen renders inside
`<div data-module="<slug>">`. Parsing first, then inserting rule by rule, is what makes the scope
hold: text spliced into a template could close the block (`} body { … }`). `@import`,
`@font-face`, `@keyframes` and anything else whose names are global are refused, and with them the
module. A browser without CSS `@scope` gets no plugin styles at all rather than unscoped ones.
The sheets are adopted while their registry is current and removed with it. The end-to-end test
checks in Chrome that the fixture's rule for the shell's `.screen-lede` changes its own screen and
not inventory's.

### The editor's Content-Security-Policy

Every page now carries one (`editor/next.config.ts`):

```
default-src 'self'; script-src 'self' 'unsafe-inline' blob:; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; media-src 'self' blob:; font-src 'self' data:; connect-src 'self';
worker-src 'self' blob:; object-src 'none'; base-uri 'self'; form-action 'self';
frame-ancestors 'none'
```

Scripts come only from the editor's origin or a `blob:` URL (how a checked bundle is evaluated),
and requests go only to the editor's origin, which proxies to the engine — so plugin code cannot
pull in code from another host, nor `fetch` the token to one. `'unsafe-inline'` stays because
Next.js writes inline scripts without nonces here; moving to nonces needs every page rendered
dynamically and is not done. Development adds `'unsafe-eval'` and `ws:` for `next dev`.

### The trust model for plugin UI

```
  who is trusted            for what                              enforced by
  ──────────────            ────────                              ───────────
  the operator's trusted    which plugins may be installed at     R5: checksum + Ed25519 signature
  keys                      all, UI included                      before anything is unpacked
  the install record        which bytes are that plugin's screen  hash taken from the signed archive
  the editor                that what runs is those bytes         SHA-384 compared before evaluation
  the plugin's UI code      everything the signed-in author can   NOTHING inside the page — by design
                            do, once it runs
```

A plugin's screen runs on the editor's origin, in the same JavaScript realm as the shell, with
the author's token reachable through `host.engine`. That is the point — it is the screen for its
app — and it means **installing a plugin is trusting its UI exactly as much as its backend**, which
already runs in-process with the service's database session (R5). The decision is made once, at
install, by whose signature the operator trusts.

What the checks above do buy:

- the bytes that run are the bytes the publisher signed: a file changed on disk after install, or
  by anything between the service and the browser, is refused and reported, never run;
- the code cannot come from, or send to, another origin (the CSP);
- a plugin cannot take a built-in's address or another plugin's, and cannot break the shell by
  failing, at load or at render;
- one plugin's CSS does not restyle another's screens by accident.

What they do not: a plugin's script can still do anything a script on the page can — read the
DOM of other screens, call any engine route as the author, add an unscoped stylesheet, register a
`blob:` script of its own. The host is frozen against accidents, not against an author who means
harm. Isolating plugin UI properly means a sandboxed iframe per plugin talking to the shell over
`postMessage`, with no token in its realm; that is the UI counterpart of R5's "out of process",
and not this release.

Someone who can write the plugins directory can also edit `installed.json`; they can equally edit
the plugin's Python, which runs with full trust. The record defends the bytes between install and
browser, not a compromised host.

### How the end-to-end test runs

`editor/e2e/plugin-ui.spec.ts` runs the Python service itself, because installing and removing a
plugin means restarting it (the service reads its plugins when it starts, as R5 decided). It builds,
signs, publishes and installs the fixture with the `wavemaker` command, then:

1. without the plugin — no Bulletin in the rail, `/bulletin` is "Nothing lives at this address";
2. installed, restarted — Bulletin in the rail marked "Installed plugin"; opening it shows the
   notice its screen fetched from `GET /api/v1/bulletin/notice` with the author's token; the page
   carries the CSP; the plugin's style reaches its screen and not inventory's;
3. `ui/module.js` changed on disk, no restart — the rail reports the integrity mismatch, no
   Bulletin link, and the marker the appended line would set is absent: the bundle never ran;
4. directory removed, restarted — no Bulletin anywhere, `/bulletin` is "Nothing lives at this
   address".

It needs `LUDUS_E2E_SERVICE_PYTHON` (a Python with the service installed), `WAVEMAKER_DATABASE_URL`
and `WAVEMAKER_JWT_SECRET`, plus the journey's variables; it serves on the host and port of
`LUDUS_ENGINE_URL`, so the editor must be started pointed there. Without
`LUDUS_E2E_SERVICE_PYTHON` it is skipped, so `npm run e2e` without a Python service runs the journey
alone. It was run locally against PostgreSQL 16 in Docker, uvicorn, and `next build && next start`,
in the installed Google Chrome (Playwright's bundled browser for 1.63 was not installed): four
passed. The journey passed against the same stack.

CI runs it in the Quickstart job, against the Python service, since R9 moved the Quickstart off
the Java engine.

### Still owed

- **Uninstall** (R5 owes it): removing a plugin is removing its directory and restarting.
- **Hot install**: the service reads plugins at start, so installing or removing needs a restart;
  the editor picks the change up on its next load of `/health` (a reload).
- **Isolation of plugin UI** in a sandboxed iframe, above; and a nonce-based CSP without
  `'unsafe-inline'`.
- **Multi-file bundles**: a bundle is one file, because it is evaluated from a `blob:` URL, where
  relative imports cannot resolve. The route serves other files (CSS, images) for a bundle to
  reference by absolute address, but only the entry is integrity-checked.
- **Plain-HTTP deployments on an address other than localhost**: the browser offers no
  `crypto.subtle` there, so a plugin's screen is refused with that reason. Serve the editor over
  HTTPS.
