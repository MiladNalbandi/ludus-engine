# R3 — players, and wallets that do not lose grants

Players, and the money they hold. `economy` is the second app and the first one that is not
about documents. The players themselves, and the API keys that let a game ask for one, are
the platform's.

## Acceptance criteria

|          | Criterion                                                                                          | State |
| -------- | -------------------------------------------------------------------------------------------------- | ----- |
| **AC-1** | An administrator mints an API key; it is shown once, stored as a digest, and can only be a viewer  | green |
| **AC-2** | A key buys a short-lived player session; no key, an unknown key and a revoked key buy nothing      | green |
| **AC-3** | Player tokens and administrative tokens are not interchangeable, in either direction               | green |
| **AC-4** | A player reads and renames themselves at `/api/v1/player/me`; no player route takes a player id    | green |
| **AC-5** | An editor grants currency; a viewer cannot; a player cannot grant themselves by any path           | green |
| **AC-6** | A player spends their own; an overdraft is refused by a CHECK constraint and answered 422          | green |
| **AC-7** | Every balance change is one statement with the arithmetic in the database                          | green |
| **AC-8** | **Twenty concurrent first grants of one coin end at twenty**, in a database of the test's own      | green |
| **AC-9** | Every new table carries `project_id` with a foreign key to `project`                               | green |

## Three credentials, and none stands in for another

```
  game build                       player                          account
  X-API-Key: wm_…                  Bearer <player token>           Bearer <access token>
       |                                 |                                |
       v                                 v                                v
  POST /public/players/session     /api/v1/player/me/**            /api/v1/admin/** by role
       |                           (and nothing else)              (and nothing else)
       +--> a player token
```

**A key cannot write player state, and that is the requirement being impossible as stated,
not a stricter reading of it.** The live-ops issue asked for a client that reads and writes
player state with an API key. A key ships inside a binary anybody can unpack, so anything it
can do, anyone can do — and a key that could write player state could write *every* player's.
The key keeps the job it is good at, saying which game is calling, and buys a token scoped to
one player. A leaked key then lets somebody play as a player of their own, which no shipped
credential can prevent. It does not let them touch anybody else.

The key goes in its own header rather than `Authorization`. Different holders, lifetimes and
powers in one header would make "which kind of caller is this" a parsing question.

**The player token has its own `typ` and its own reader.** `read` refuses a player token and
`read_player` refuses an access or refresh token, and a player comes back as `PlayerCaller`,
a different type from the `Caller` every admin guard takes. It carries no role, so there is
no role claim to be trusted or forgotten. Tests go in both directions and include an
administrator's token whose subject is the player's own uuid.

It lives an hour and cannot be revoked, for the same reason an access token cannot: it is
checked by its signature alone. Revoking a key stops new sessions, not ones already issued.

## The rule this app exists to keep

```
  Java, first grant to a player with no row         here
  ------------------------------------------        -----------------------------------------
  update … set amount = amount + 1   (0 rows)        insert … values (…, 1)
  insert …                           (races)           on conflict (player_id, currency)
    one wins, the rest: unique violation               do update set amount = balance.amount
    -> "refused"                                                          + excluded.amount
                                                     returning amount
  20 grants -> 18 coins                              20 grants -> 20 coins
```

PostgreSQL guarantees an `insert … on conflict do update` either inserts or updates,
atomically, whoever else is trying. There is no "no row yet" branch, so there is nothing on it
to get wrong. A spend is one `update … set amount = amount - :n`, and it never reads the
balance first.

**The concurrency test was checked by breaking it.** With the Java's update-then-insert path
put back for one run, every round failed: 16 to 18 of the 20 grants were told "refused". With
the upsert, the twenty reported balances are 1 to 20, each exactly once — which is a stronger
claim than "the total is twenty", since it says no two grants read the same starting point.
It runs five rounds, each against a player with no row at all.

**It has a database of its own.** Its rows are committed by twenty worker threads and nothing
can roll them back. The Java's version shared its module's database, collided with another
test's rows, and passed locally while failing on CI. Here a fixture creates a database for the
test, migrates it, and drops it afterwards, so the isolation is structural rather than a
question of who runs first.

**The overdraft is the schema's to refuse.** `ck_economy_balance_not_negative` is tested by an
update straight to the table, past the application, and a spend is checked to be exactly one
`update` with no `select` in front of it. Twenty concurrent spends of one coin from ten let
exactly ten through. The refusal reaches the client as 422 naming the currency, never as 500.

## Decisions

**Players and API keys are the platform's, not the economy app's.** Inventory, leaderboards and
progression all need a player, and apps may not import each other. So the `player` table, the
session route and `GET /api/v1/player/me` live in `platform/identity`; `economy` knows a player
only by the id a verified token or an editor gives it, and the wall check stays green. The
brief for this release put `/player/me` in the economy app. It is here instead, because a
player's profile should not disappear when the wallet is switched off.

**No player route takes a player id.** A route shaped `/players/{id}` authorised by "is a
player" lets any player act as any other, and the check that prevents it is one somebody has to
remember in every handler. A test reads the service's own OpenAPI and fails if a `{` ever
appears under `/api/v1/player`.

**A grant does not look the player up first.** The composite foreign key to `player (id,
project_id)` refuses a player who is not in this project, inside the same statement, so there
is no read with a gap after it for a delete to fall into. A grant to an unknown player is 404.

**A grant cannot add to another project's balance.** The table's key is `(player_id,
currency)`, as the Java's was, so a grant naming a player from another project would
*conflict* with that project's row — and `do update` would add to it. The foreign key never
fires, because nothing is inserted. The upsert carries `where balance.project_id =
excluded.project_id`, and a test grants from one project to a player who already holds coins
in another and checks their balance does not move. Without that `where`, the test fails.

**Starting a session is an upsert too.** Find-then-insert has the wallet's race one table over:
two requests from a first launch both find nothing, both insert, and one fails — on exactly the
path where a client is least able to recover. Eight concurrent first sessions for one
identifier resolve to one player.

**The table is `economy_balance`, not the Java's `player_currency`.** The design gives each app
tables under its own prefix, and this is the first app table written since.

**No in-memory wallet.** The rules this port exists for are kept by PostgreSQL. A fake would be
a second implementation of exactly those rules, passing tests the real one might fail.

**Two answers differ from the Java, and the contract wins both.**

- `createApiKey` answers **200**. The frozen contract says 200; the Java answered 201, which was
  a drift in the Java rather than the contract.
- A session request with no usable `externalId` is **422**, not the Java's 400. The body was
  read and is not acceptable, which is what 422 means everywhere else in this service.

**Validation that a database cannot do, and nothing more.** A currency is
`^[a-z0-9_]+$` up to 40 characters, and an amount is a whole number from 1 to the largest
bigint; `{"amount": true}` is refused even though Python calls `bool` an int. A grant that
would overflow a bigint in the database is 422, not 500.

## What changed in earlier tests

- The skeleton test and both `/health` tests list a built-in `economy` app beside `content`.
- `/health`'s test plugin called `economy` is now `leaderboard`, since an installed plugin may
  not take a built-in app's name.
- The R1b `/health` test now checks `content` is listed rather than that it is the only app.

## Still owed

- **`listPlayers` and `getPlayer`** (`GET /api/v1/admin/players`, `/players/{id}`). Not needed
  for a session or a wallet. The list is cursor-paged on `last_seen_at`, which is R6's keyset
  work, and both belong with it.
- **`rewardPlayer`** (`POST /api/v1/admin/players/{id}/reward`) grants currency *and* XP in one
  transaction. XP is progression, which is R6.
- **Currency routes.** The contract has none: no catalogue, no route to list or define a
  currency. A currency exists when something is granted in it. If a catalogue is wanted, it is
  a contract change and a decision, not something to slip in here.
- Revoking a key does not end sessions it already bought; they run out within the hour.
