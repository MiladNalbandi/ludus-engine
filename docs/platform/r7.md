# R7 — media: audio and sprites, streamed

A `media` app: upload, list and delete audio clips and sprites behind a role, serve them to
anybody, and mix clips into new ones with FFmpeg. Metadata lives in PostgreSQL; the bytes live
on the filesystem behind a blob store that now belongs to the platform.

## Acceptance criteria

|          | Criterion                                                                                | State |
| -------- | ---------------------------------------------------------------------------------------- | ----- |
| **AC-1** | Upload, list and delete, for audio and sprites, behind a role; a viewer may only list    | green |
| **AC-2** | The public routes stream the bytes, cached immutably, with an ETag and a 304             | green |
| **AC-3** | **A 12 MB upload and a 12 MB download are streamed, never held whole in memory**         | green |
| **AC-4** | SVG is refused as a sprite, decided from the bytes and not the label                     | green |
| **AC-5** | A wrong type is a 415, too large a 413, empty a 422 — never a 500, and nothing left on disk | green |
| **AC-6** | A storage path cannot escape its directory: ids are generated, a filename is a label     | green |
| **AC-7** | Mixing runs FFmpeg with an argument list, never a shell; the mix is an ordinary clip     | green |
| **AC-8** | **A process that hangs is killed at its limit: a one-second limit takes about a second** | green |
| **AC-9** | Unset means off and says so; a blob directory that cannot be written stops the start     | green |

## The contract

All seven media operations in `docs/api/openapi-v1.json` are implemented, at their paths and
with their field names:

| Operation         | Route                                | Answers                     |
| ----------------- | ------------------------------------ | --------------------------- |
| `listAudioClips`  | `GET /api/v1/admin/audio`            | 200, `AudioClipSummary[]`   |
| `uploadAudioClip` | `POST /api/v1/admin/audio`           | 201, `AudioClipSummary`     |
| `mixAudioClips`   | `POST /api/v1/admin/audio/mix`       | 201, `AudioClipSummary`     |
| `deleteAudioClip` | `DELETE /api/v1/admin/audio/{id}`    | 204                         |
| `streamAudioClip` | `GET /api/v1/public/audio/{id}`      | 200 streamed, or 304        |
| `listSprites`     | `GET /api/v1/admin/sprites`          | 200, `SpriteSummary[]`      |
| `uploadSprite`    | `POST /api/v1/admin/sprites`         | 201, `SpriteSummary`        |
| `deleteSprite`    | `DELETE /api/v1/admin/sprites/{id}`  | 204                         |
| `streamSprite`    | `GET /api/v1/public/sprites/{id}`    | 200 streamed, or 304        |

**One deliberate difference from the document, kept from R2:** it lists `200` for every
operation, because springdoc writes the default when an annotation says nothing. The Java
engine actually answered `201` on upload and mix and `204` on delete, and those are what a
real client has been receiving. Python answers what Java answered, as the content app does.

Viewers may list, which the Java did not allow — it put all of `/admin/audio/**` behind
EDITOR. The content app already lets a viewer read drafts, and a list of clip names is less
than that.

## Streamed, and measured rather than argued

```
   socket ──64 KiB──▶ multipart parser ──▶ blob writer ──▶ <id>.partial ──rename──▶ <id>
                      (python-multipart,    counts, hashes,
                       driven by hand)      keeps first 64 B
```

The upload never goes through `request.form()`. Starlette's form parsing would hold up to a
megabyte of each file in memory, spool the rest to a temporary file, and only then hand the
route an `UploadFile` — which would then be copied into the store, so every byte is written
twice, and an oversized upload is refused only after it has been written to the temporary
directory in full. Here the parser is driven chunk by chunk, each chunk goes to its final
directory once, and the limit is counted at the chunk that crosses it. A declared
`Content-Length` over the limit is refused before a byte is read.

The download is a `StreamingResponse` over the open file, 64 KiB at a time.

The test does not trust any of that. `TestClient` cannot prove streaming: httpx reads a
streamed request body whole before the application sees it, so memory measured through it is
the test's own copy. The test calls the ASGI application directly instead, hands it one shared
64 KiB buffer at a time, throws each response chunk away as it arrives, and measures with
`tracemalloc`, which sees every Python allocation in every thread:

| 12 MB                     | Peak traced memory |
| ------------------------- | ------------------ |
| Upload                    | 0.1 MiB            |
| Download                  | 0.2 MiB, largest chunk 64 KiB |
| Upload, with the writer made to keep its chunks (a deliberate break) | **24.0 MiB — test fails** |
| Download, with `stream.read()` in place of the loop (a deliberate break) | **one piece — test fails** |

Both breaks were made, watched fail, and reverted, so the test is known to guard something.

## The timeout that never timed out

The Java read FFmpeg's output and then waited with a limit. Reading blocks until the process
closes its output, so a process that hung was waited on forever before the limit was ever
consulted, and a test with a one-second limit took thirty seconds to fail. Reading after the
wait is no fix: it deadlocks the other way, once the process fills a pipe buffer nobody is
draining.

```
   Java:    read(stdout) ─────────── blocks until the tool exits ───────────▶ wait(1s)
   here:    stdout ─▶ file           wait(1s) ─▶ kill the process group ─▶ raise
```

Output goes to a file in the job directory. The only thing the runner blocks on is
`wait(timeout)`, and the tool has nothing to block on either. The process gets its own process
group and is killed as one, so a tool that forks cannot leave a child running past the limit.

The tests use a stand-in for FFmpeg — the Python running them — so the timeout is proved on a
machine with no FFmpeg at all:

- a process that sleeps for a minute, under a one-second limit: stopped in under two seconds;
- a process that writes ten megabytes and then sleeps — far past any pipe buffer: the same;
- a process whose forked child would outlive it: the child is gone too;
- through `POST /admin/audio/mix` with `mix_timeout_seconds=1`: a 503 in under 2.5 seconds.

Putting the Java's order back (`communicate()` before the timed wait) makes the first test
take **62 seconds** and fail. That is the same bug, reproduced, and the reason the test exists.

## SVG, and why the bytes are checked

A sprite is served from this service's own origin with the type it was stored under, and an
SVG is XML that may carry `<script>`. Refusing `image/svg+xml` is not enough, because the
label is only what the client chose to say. A sprite is accepted only when:

1. its declared type is PNG, JPEG, WebP or GIF — checked before a byte is written, so a wrong
   type costs nothing;
2. its first bytes carry that format's signature — and anything beginning like markup (after
   a byte-order mark and whitespace) is refused as SVG, whatever it claims to be;
3. the two agree. A PNG sent as `image/jpeg` is refused rather than relabelled: two sources
   for one fact, and picking either would mean serving a type nobody checked.

Everything served carries `X-Content-Type-Options: nosniff` and
`Content-Security-Policy: default-src 'none'; sandbox`, so even a file that slipped past would
be neither guessed into a document nor able to run anything.

Audio is checked by label only, as in the Java. Audio formats have no single reliable
signature, and with `nosniff` a mislabelled clip is never treated as a document.

## Where the bytes go

```
WAVEMAKER_BLOB_DIRECTORY/
  media-audio/<uuid>        one namespace per kind, so audio and sprites
  media-sprites/<uuid>      cannot land in each other's directory
```

The blob store moved into the platform (`wavemaker.platform.storage.blobs`) rather than living
in the media app. Every app that keeps an upload needs the same rules — write beside the name
and rename when whole, count against a limit, name files only by a UUID — and the Java learned
them once already. Only a `uuid.UUID` can name a file: a string that merely *looks* like one is
a `TypeError`, because the type is the guarantee and text has skipped the parse that makes the
path safe. A client's filename is a label, cut to its last segment, stripped of control
characters and capped at 255.

The `If-None-Match` reader moved the same way, into `wavemaker.platform.http.etag`, because
apps may not import each other and media needed exactly what content has. Content still has
its own copy; moving it onto the platform one is a small follow-up.

## Configuration

| Setting                               | Default  | Meaning                                                          |
| ------------------------------------- | -------- | ---------------------------------------------------------------- |
| `WAVEMAKER_BLOB_DIRECTORY`            | _(none)_ | Where uploads are written. Unset: media answers 503. Must be a volume under Docker |
| `WAVEMAKER_MEDIA_MAX_AUDIO_BYTES`     | 64 MiB   | Per clip                                                         |
| `WAVEMAKER_MEDIA_MAX_SPRITE_BYTES`    | 16 MiB   | Per sprite                                                       |
| `WAVEMAKER_MEDIA_FFMPEG_BINARY`       | _(none)_ | An absolute path. Unset: mixing answers 503                      |
| `WAVEMAKER_MEDIA_MIX_TIMEOUT_SECONDS` | 60       | A hard stop on one mix                                           |
| `WAVEMAKER_MEDIA_MIX_MAX_TRACKS`      | 8        | Tracks per mix                                                   |
| `WAVEMAKER_MEDIA_MIX_MAX_OUTPUT_BYTES`| 64 MiB   | Passed to FFmpeg as `-fs`, and checked after it exits            |

No path has a default. An unset blob directory is "this service stores no files", not a
directory inside the container that works until the next deploy and then has lost every
upload. A set one that cannot be written stops the start, while somebody is watching. An FFmpeg
path must be absolute: a name looked up on `PATH` is whatever ffmpeg means on this machine
today.

## Errors

- **415** a type this service will not store: SVG as a sprite, `text/html` as audio, a label
  that disagrees with the bytes, or a body that is not `multipart/form-data` at all.
- **413** larger than the limit — refused up front when the length is declared, cut off at the
  crossing chunk when it is not, with the rest of the body left unread.
- **422** an empty file, a form with no `file` part, or a mix naming a clip that is not here
  (`/tracks/1: ...`), a bad gain (`/tracks/0/gainDb`), or one the mixer could not combine.
- **400** a body that says it is multipart and cannot be read as such.
- **503** media or mixing is not configured, or a mix ran past its limit.
- **404** an unknown id, a malformed one, an id of the other kind, or a row whose bytes are
  gone — all the same answer, because telling them apart only tells a caller which ids exist.

FFmpeg's own output is logged and never returned: it names paths inside the container.

## Migration

`0004_media.py` creates `audio_clip` and `sprite`, the Java's V5 and V12 with one column
added: `content_sha256`, the ETag, computed while the upload streams. It names **0002** as its
parent, because 0003 was being written in parallel. Once both have landed there are two heads;
rebasing this one onto 0003 is a one-line change to `down_revision`.

## Still owed

- **The volume.** Nothing here builds the image or mounts a volume, so "an upload survives a
  restart" is not proved by `pytest`. The Java CI had a step that uploads, restarts the
  container and diffs the bytes; the Python deployment needs the same step and a volume at
  `WAVEMAKER_BLOB_DIRECTORY`.
- **FFmpeg in CI.** The real-FFmpeg test skips, with its reason, where FFmpeg is not installed.
  Everything else about mixing — the argument list, the timeout, a failing or oversized tool —
  runs against a stand-in everywhere.
- **Orphaned bytes.** A crash between the rename and the row leaves a file nobody can name.
  It is invisible and harmless, as in the Java, and nothing sweeps it up yet.
