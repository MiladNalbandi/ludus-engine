# R4 — inventory, the first app built plugin-first

What a player owns. An `inventory` app: a catalogue of items a project defines, each with a
free-form `attributes` document checked against a JSON Schema the project supplies, and the
quantities each player holds. It is the first app written as a package that will be installed
rather than one that happens to live in this repository.

## Acceptance criteria

|           | Criterion                                                                                          | State |
| --------- | -------------------------------------------------------------------------------------------------- | ----- |
| **AC-1**  | An editor defines, replaces, lists and deletes items; a viewer and an anonymous caller cannot       | green |
| **AC-2**  | Attributes are a JSON object, kept as the exact text sent, with a generated `jsonb` beside it       | green |
| **AC-3**  | Attributes are validated against the project's schema; every violation at `/attributes` + pointer | green |
| **AC-4**  | **A schema is an object or a boolean: an array is refused**, as is one too large or unusable        | green |
| **AC-5**  | **A remote `$ref` is refused, and nothing is ever fetched** — proved by watching the network        | green |
| **AC-6**  | A grant is all or nothing; a negative quantity takes away; below zero is refused by a CHECK         | green |
| **AC-7**  | A player reads their own at `/player/me/inventory`; player and admin tokens are not interchangeable | green |
| **AC-8**  | Twenty concurrent first grants of one arrow make twenty; twenty takes from ten let ten through      | green |
| **AC-9**  | Every table carries `project_id` with a foreign key to `project`; rows cannot cross projects        | green |
| **AC-10** | Whatever a caller sends is a 4xx naming the field, never a 500                                      | green |
| **AC-11** | The package imports only `wavemaker.platform`, and nothing in it names where it is installed       | green |

The issue's "done when" is the four tests named in it: an item type with attributes is defined
(`test_ac3_attributes_that_satisfy_the_schema_are_saved`), a player is granted an instance
(`test_ac6_an_editor_grants_several_items_and_the_player_sees_them`), an array is refused as a
schema (`test_ac4_a_schema_that_is_not_an_object_or_a_boolean_is_refused`, at both layers), and
a remote `$ref` is refused (`test_ac5_*`).

## The contract

All nine inventory operations in `docs/api/openapi-v1.json` are implemented, at their paths,
with their operation ids and their field names. A test reads the contract file and checks the
service's own OpenAPI answers each one where the contract says.

| Operation                   | Route                                              | Who            | Answers                   |
| --------------------------- | -------------------------------------------------- | -------------- | ------------------------- |
| `listItems`                 | `GET /api/v1/admin/items`                          | EDITOR, ADMIN  | 200, `ItemView[]`         |
| `getItem`                   | `GET /api/v1/admin/items/{id}`                     | EDITOR, ADMIN  | 200, `ItemView`           |
| `saveItem`                  | `PUT /api/v1/admin/items/{id}`                     | EDITOR, ADMIN  | 200, `ItemView`           |
| `deleteItem`                | `DELETE /api/v1/admin/items/{id}`                  | EDITOR, ADMIN  | 204                       |
| `getItemSchema`             | `GET /api/v1/admin/item-schema`                    | EDITOR, ADMIN  | 200, the schema           |
| `replaceItemSchema`         | `PUT /api/v1/admin/item-schema`                    | EDITOR, ADMIN  | 200, the schema           |
| `getPlayerInventoryAsAdmin` | `GET /api/v1/admin/players/{id}/inventory`         | EDITOR, ADMIN  | 200, `PlayerInventory`    |
| `grantPlayerItems`          | `POST /api/v1/admin/players/{id}/inventory/grant`  | EDITOR, ADMIN  | 200, `PlayerInventory`    |
| `getPlayerInventory`        | `GET /api/v1/player/me/inventory`                  | player token   | 200, `PlayerInventory`    |

**Where the answers differ from the document, and why:**

- `deleteItem` answers **204**. The document lists 200 because springdoc writes the default when
  an annotation says nothing; the Java answered 204, and that is what a client has received.
  This is the same rule R2 and R7 follow.
- `grantPlayerItems` answers with **everything the player then holds**. The Java answered with
  only the lines it had changed. `PlayerInventory` is described by the contract as "everything a
  player holds", the player route answers with that, and one shape read from two routes should
  mean one thing. A client that read only the changed lines finds them in the full list.
- `ItemRequest.attributes` and `ItemView.attributes` are **JSON text inside a string**, as the
  contract types them (`"type": "string"`) and as the Java bound them, so the characters an
  editor wrote reach the database untouched. A nested object is refused with a 422 at
  `/attributes` rather than accepted, because accepting it means serialising it to store it.

**One scope note.** The issue asks for "an item type catalogue" with attributes "validated
against a JSON Schema the project supplies". The contract has one schema per *project*, at
`/admin/item-schema`, and one catalogue of items each carrying an `itemType` from the project's
own vocabulary. That is what is built. A schema per item type would be a contract change.

## The two traps the Java fell into

### An array is not a schema

```
  Java:  "[1, 2, 3]"  ──▶ networknt compiles it ──▶ a schema that validates nothing
         test: assertThatThrownBy(...).isInstanceOf(SchemaUnusable)   ── passed? no: it was
         accepted, and every item would have passed validation

  here:  "[1, 2, 3]"  ──▶ parsed ──▶ not an object, not a boolean ──▶ 422, before any library
```

A JSON Schema is an object or one of the two booleans; that is what the specification says. The
shape is checked by the domain (`domain/attribute_schema.py`), not left to whatever the library
tolerates, and a test replaces the library's `check_schema` with a function that fails if it is
ever called with the array. The library this service uses happens to refuse an array too — a
lenient library is not a reason to be lenient, and a strict one is not a reason to rely on it.

`5`, `"object"` and `null` are refused the same way, as are a schema over 64 KiB, nested past 64
levels, not UTF-8, naming a dialect other than 2020-12, failing the meta-schema (`"type":
"nope"`, a `pattern` Python cannot compile), or holding a local reference that points at nothing.
Each is refused when the schema is **set**, not on the first item somebody tries to save.

### A remote `$ref` is never fetched

Two independent layers, and the tests watch the network for both:

```
  PUT /admin/item-schema
     │
     ▼
  domain: parse, then walk every node ───── "$ref", "$dynamicRef", "$recursiveRef" whose
     │                                       target does not begin '#'  ──▶ 422 at its pointer
     ▼
  adapter: jsonschema, with a registry whose only way to retrieve a resource is to refuse
                                              ──▶ unresolvable, 422 — never a request
```

**The library's default is to fetch.** A `jsonschema` validator built the ordinary way resolves a
reference it does not hold by calling `urlopen`, and only warns that it did. One test proves it:
with `urlopen`, `socket.create_connection`, `socket.getaddrinfo` and `socket.connect` replaced by a
tripwire, a default validator for `{"$ref": "https://attacker.example/…"}` trips it. The same
tripwire stays silent for every schema the service handles, including one written straight into
the table past the first check — the case where only the second layer stands.

**The Java's check could be walked around.** It matched `"$ref"` in the schema *text* with a
regular expression. `{"$ref": "https://…"}` is the same key once parsed, and the pattern
never sees it. Here the document is parsed first and the walk reads the parsed tree, so what is
checked is exactly what the validator will act on; a test sends the escaped form.

The walk is deliberately blunt: it refuses a remote-looking `$ref` even where it is data rather
than a keyword (inside `const`, `enum`, `examples`). Telling the two apart means knowing every
keyword of every dialect that holds an instance, and getting one wrong is a fetch. Refusing one
that would have been ignored costs an author one edit.

A local reference is allowed because it fetches nothing — including under a `$id` naming a
foreign host, since a reference beginning `#` resolves against a resource the schema itself
declared. Both are tested with the tripwire on.

## Documents, kept as they were sent

```
  inventory_item
    attributes_json  text   what the editor sent — served back byte for byte
    attributes       jsonb  generated from it — for "every item whose element is fire"
```

The same pair as a wave's, for the same reason: `jsonb` reorders keys and rewrites `2.0`, and an
editor should read back what they wrote. The schema is stored as text only; it is never queried.

**Everything a caller can send is refused before it reaches the database.** Python's JSON
reader accepts several things the rest of the system will not, and each would otherwise be a
500:

| Sent                               | Python reads it as     | Would have failed at                    |
| ---------------------------------- | ---------------------- | --------------------------------------- |
| `NaN`, `Infinity`                  | a float                | `jsonb`: not JSON                       |
| `1e400`                            | infinity               | validation of a number nobody wrote     |
| `"\u0000"`                         | a string with NUL      | PostgreSQL text cannot hold NUL         |
| `"\ud800"`                         | a lone surrogate       | encoding to UTF-8 for the driver        |
| `[[[[…5000 deep…]]]]`              | `RecursionError`       | the request                             |
| `1e-1000000`                       | `0.0`                  | `numeric` underflow, in PostgreSQL      |

The first five are refused by the domain with a pointer to the value. The last is found by
PostgreSQL, and the adapter turns its data exception into a 422 at `/attributes` — the backstop
for anything Python reads and `jsonb` does not. The same text checks apply to `name` and
`spriteRef`.

A `spriteRef` is an opaque label the game resolves. It is never a URL this service fetches.

## Grants: one statement, all or nothing

```
  POST …/inventory/grant  {"items": [{"itemId":"sword","quantity":1}, {"itemId":"arrow","quantity":-3}]}

  begin
    select 1 from player … for key share          the player cannot be deleted mid-grant
    savepoint ─ give sword:  insert … on conflict do update set quantity = quantity + 1
    savepoint ─ take arrow:  update … set quantity = quantity + (-3)    CHECK (quantity >= 0)
  any line refused?  rollback everything, 422 naming every refused line
  otherwise          commit, answer with everything the player holds
```

**A give is an upsert; a take is an update, and never an upsert.** This was found by a test,
not foreseen: PostgreSQL checks a proposed row's constraints *before* it looks for a conflict,
so an upsert proposing quantity `-3` is refused by `ck_inventory_entry_not_negative` even when
the row it would have added to holds ten. The first version did exactly that, and the tests for
"a negative quantity takes away" and for twenty concurrent takes both failed. A take from no row
at all is no take: "the player does not have 3 of 'arrow'", or "no item 'arrow' in this project"
when the item is not defined.

**A savepoint per line.** A failed statement aborts a PostgreSQL transaction, so without them the
first bad line would hide every other one. With them each line is tried, every refusal is
collected, and everything is rolled back together. A player who received the sword and not the
shield has been given something the game never offered, and the inventory would look perfectly
consistent.

**The player is locked, not looked up.** `for key share` is the weakest lock that stops the row
being deleted, and it is held to the end of the grant, so there is no gap between "the player
exists" and the last line. It also makes "no such player" one answer, 404, whatever the lines
were.

**The concurrency tests** run twenty threads on twenty connections in a database of their own,
released together by a barrier. Twenty first grants of one arrow to a player with no row report
1 to 20, each exactly once, and end at twenty. Twenty takes of one from ten let exactly ten
through, refuse the other ten as refusals rather than errors, and end at zero.

## Decisions

**The project is in the inventory row's key.** The Java keyed it `(player_id, item_id)`, the
wallet's shape — and R3 found that shape needs a `where` on the upsert, or a grant from one
project adds to another project's row. With `(project_id, player_id, item_id)` the two can never
conflict, so there is nothing for the `where` to catch. Both foreign keys are composite with the
project, so a row pairing a player from one project with an item from another is not insertable;
a test tries it directly, claiming each project in turn.

**Items are an editor's, and a viewer sees none of them.** As in the Java's authorisation
matrix, where `/admin/items`, `/admin/item-schema` and `/admin/players/**` were EDITOR. The
content and media apps let a viewer read; an item catalogue tells a reader what every item is
worth, which is closer to the economy than to a list of clip names.

**A grant of nothing, or of zero, is refused.** Both change nothing, so whoever sent them meant
something else. A grant is at most 100 lines: one transaction holds a row lock per line, and a
batch job should not hold them on one request.

**A row at zero is kept.** "Had three arrows and used them" is worth telling apart from "never
had one" when a game shows a collection.

**Every violation is reported, not the first.** The detail is one string — `/attributes/damage:
0 is less than the minimum of 1; /attributes/element: 'mud' is not one of …` — in pointer order,
the first twenty and a count of the rest. One string keeps the error shape every other route in
this service has; listing them all keeps an editor from fixing a document one round trip at a
time.

**Tightening the schema does not re-validate existing items.** They stay readable and are
checked on their next save. Otherwise half a catalogue becomes unsaveable with nothing saying
which half; a migration is the honest way to handle that.

**No in-memory store.** The rules the storage port exists for — one project per row, nobody below
zero, all of a grant or none — are kept by PostgreSQL. A fake would be a second implementation of
exactly those rules.

## Built to be installed

```
apps/inventory/
  manifest.toml          name, version, the platform it needs
  __init__.py            exposes `router`
  domain/                items, grants, the schema rules — plain Python
  application/           the use cases, and the ports they need
  adapters/              HTTP, PostgreSQL, jsonschema
```

Three things are checked by a test that reads every import in the folder, so a convenient
shortcut added later fails here rather than in R5:

- it imports nothing of this repository except `wavemaker.platform`;
- **every import inside the package is relative**, so nothing names where it is installed —
  moving the folder out of `wavemaker.apps` changes no line of it;
- nothing walks out of the folder to find a file, as the content app does for its wave schema.

What R5 still has to solve, and what this release could not do from inside the folder:

- **Migrations.** The tables are in the platform's history, `0005_inventory.py`, because that is
  the only history the service runs. A plugin carrying its own migrations, and the platform
  running them, is R5's.
- **Mounting.** The platform imports an app as `wavemaker.apps.<name>`. An installed package will
  live elsewhere; the package itself does not care, but the loader does.
- **Python dependencies.** The app imports `jsonschema` and `referencing`. They are in the
  service's `pyproject.toml` (`referencing` added explicitly now, since the app imports it
  directly). A manifest has no way yet to say what a plugin needs installed.

## Migration

`0005_inventory.py` creates `inventory_item_schema`, `inventory_item` and `inventory_entry`, with
`down_revision = "0004m"`, the single head on main when this was written. Another release is
adding `0006` in parallel; the two are joined by the maintainer, as R3 and R7 were by `0004m`.

## What changed in earlier tests

- The skeleton test and the `/health` test list a built-in `inventory` app.
- `/health`'s test plugin called `inventory` is now `achievements`, since an installed plugin may
  not take a built-in app's name; the duplicate-name test uses `achievements` too, so it still
  tests two *installed* plugins colliding rather than one colliding with the built-in.

## Still owed

- **A pathological `pattern`.** A schema may carry a regular expression that backtracks
  catastrophically, and Python's `re` has no timeout. An editor could make every later save of
  an item spin a worker thread. The fix is a regex engine with a time limit, or refusing
  patterns with nested quantifiers when the schema is set; neither is done.
- **Who changed what.** A grant records no actor and no reason. The Java had none either; an
  audit trail belongs with the live-ops work, not here.
- **Request bodies are read whole** by FastAPI on every route but the schema's, which stops at 64
  KiB plus one byte. A size limit for JSON bodies belongs to the platform, for every app at once.
