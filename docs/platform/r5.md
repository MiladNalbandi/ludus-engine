# R5 — publish and install a plugin

The release that turns WaveMaker from a modular backend into a platform. Until now an app was a
folder in this repository. After R5 an app is a **package**: built once, signed, published to a
registry, and installed into any service — which then serves its routes, owns its tables and is
held to what its manifest says it may do.

```
  you build it               you publish it                  a service installs it
  apps/inventory/   ──▶   inventory-1.0.0.wmp   ──▶   wavemaker plugin install inventory@1.0.0
  wavemaker plugin build    + index.json entry                     │
                            (sha256, Ed25519 signature)            ▼
                            wavemaker plugin publish      checked, unpacked, imported,
                                                          its migrations run and judged,
                                                          its routes mounted
```

## Acceptance criteria

|           | Criterion                                                                                                   | State |
| --------- | ----------------------------------------------------------------------------------------------------------- | ----- |
| **AC-1**  | A package is one archive built from an app folder: manifest, code, migrations, optional ui — the same bytes every time | green |
| **AC-2**  | Install checks the checksum **and** the signature, with a trusted key, before anything is unpacked or imported | green |
| **AC-3**  | Unpacking is safe: traversal, absolute paths, links, devices, foreign entries, duplicates and bombs refused   | green |
| **AC-4**  | A package that does not fit is refused: platform range, a built-in's name, an overlapping prefix, a missing dependency | green |
| **AC-5**  | An installed plugin is imported and mounted like a built-in, and may not shadow `wavemaker`, the standard library or anything installed | green |
| **AC-6**  | Its routes lie under `/api/v1/<name>` or a prefix it declares, and none answers a path another app answers   | green |
| **AC-7**  | **Its own migrations run, in its own version table, and are judged by what they did: a table outside its prefix is refused, by name, and rolled back** | green |
| **AC-8**  | Outbound network is refused to a plugin unless its manifest grants it                                        | green |
| **AC-9**  | **A service with no `inventory` folder installs the inventory package and serves inventory**                   | green |
| **AC-10** | `[permissions]` is read strictly: an unknown key, a grant that does not exist, a route that is not a fixed path — refused | green |

The issue's two done-criteria are AC-9 and AC-7:

- **AC-9** — `test_ac9_a_service_with_no_inventory_folder_installs_the_package_and_serves_inventory`
  (`tests/integration/test_inventory_installed.py`).
- **AC-7** — `test_ac7_a_plugin_asking_for_a_table_outside_its_prefix_is_refused_at_install`
  (`tests/integration/test_plugin_install.py`), and the eighteen cases of
  `test_ac7_a_migration_touching_what_is_not_its_own_is_refused_and_rolled_back`
  (`tests/integration/test_app_migrations.py`).

Run one criterion: `cd service && python -m pytest -q -k ac7`.

## How the first done-criterion is proved

"A service with no inventory folder" is taken literally, not approximated with a setting:

```
  test process                                   child process  (PYTHONPATH = the copy only)
  ────────────                                   ─────────────
  copy src/wavemaker  ─ minus apps/inventory ─▶  asserts: wavemaker comes from the copy,
  build apps/inventory/ → inventory-1.0.0.wmp            find_spec("wavemaker.apps.inventory") is None
  sign it, publish to a registry directory       wavemaker plugin install inventory@1.0.0
  an isolated PostgreSQL database                create_app(plugins_directory=…)
                                                 editor: PUT /admin/items/sword, GET /admin/items
                                                 editor: POST /admin/players/{id}/inventory/grant
                                                 player: GET /player/me/inventory  → sword × 2
  ◀── JSON: statuses, bodies, where the `inventory` module was loaded from ──
  asserts the module file is under plugins/inventory/, the version table says 0001,
  and the ledger says inventory owns its three tables
```

## The package

```
inventory-1.0.0.wmp                  a zip archive
  manifest.toml                      [plugin] and [permissions]
  backend/                           the Python package: __init__.py, domain/, application/, adapters/
  migrations/                        the app's own Alembic revisions
  ui/                                optional, carried and unpacked; nothing serves it until R8
```

`wavemaker plugin build <app-folder>` makes it. The app folder's `manifest.toml`, `migrations/`
and `ui/` go to the top; everything else is code, under `backend/`. `__pycache__`, `*.pyc`,
`tests/` and dot-files are left out; a symbolic link in the folder stops the build.

**Zip, built reproducibly.** Entries sorted, every timestamp the format's earliest, every mode
`0644`. The same folder always makes the same bytes, so the checksum in the index is a fact
about the source and a rebuild can be compared with what was published. Zip over tar because a
zip's central directory can be read and every entry checked before one byte is written; tar has
to be read as a stream.

**The manifest, as R5 reads it:**

```toml
[plugin]
name = "inventory"
version = "1.0.0"
requires_platform = ">=0.1"
python_dependencies = ["jsonschema>=4.23.0", "referencing>=0.35.0"]

[permissions]
tables = "own"                                      # the only grant there is
routes = [                                          # on top of /api/v1/inventory
    "/api/v1/admin/items",
    "/api/v1/admin/item-schema",
    "/api/v1/admin/players/{player_id}/inventory",
    "/api/v1/player/me/inventory",
]
outbound_http = false                               # the default
```

Inventory's routes are the frozen v1 contract's, under `/admin` and `/player/me`, not under
`/api/v1/inventory`, so it declares them. A declared route must be a fixed path under `/api/v1/`
whose first segment is text: `/api/v1`, `/api/v1/{anything}` and `/api/v1/../admin` are refused
when the manifest is read. An unknown key — `outbound_htpp` — is refused too, rather than
quietly falling back to a default.

`python_dependencies` closes one of the three things R4 said it owed: a plugin can say what it
imports beyond the platform. Install checks each against what is installed and refuses with a
list of what is missing. **It never installs one**: installing a Python package runs its build,
which is code from a third party nobody signed.

## The registry, and trust

```
registry/
  index.json        {"format": 1, "plugins": [{"name", "version", "file", "sha256", "key", "signature"}]}
  inventory-1.0.0.wmp
```

A directory — a mounted share, a checkout, a bucket synced to disk. The installer never reaches a
network for it, and the install command will stay the same when a server replaces the directory.

**What is signed is a statement, not just the bytes:**

```
wavemaker-plugin-v1
inventory
1.0.0
<sha256 of the archive>
```

Ed25519, with the `cryptography` package. Signing the bytes alone would let anybody who can edit
`index.json` relabel a genuine `inventory-0.9.0.wmp` as 1.0.0, and its signature would still
verify. The index itself is not signed and does not need to be: an edited index can only make an
install fail.

**Trusted keys** are PEM files an operator puts in `WAVEMAKER_TRUSTED_KEYS_DIRECTORY`. A key is
known by the first sixteen hex digits of the SHA-256 of its raw bytes, which is what the index
entry names. No directory, or an empty one, trusts nobody — there is no "trust on first use".
`wavemaker plugin keygen` writes a key pair; `wavemaker plugin publish` signs and lists.

### Install, in the order that is the security

```
  1  find name@version in the index
  2  read the archive's bytes              bounded (64 MiB), into memory
  3  sha256 == the index's                 ── else refuse ┐  nothing unpacked,
  4  signature verifies, key is trusted    ── else refuse ┘  nothing imported
     ── from here on these are the bytes the publisher signed ──
  5  every zip entry checked; manifest read from memory
  6  the manifest is the name and version that was signed
  7  platform range fits; no built-in's name; no installed app's name or prefix;
     a module name nobody else has; the Python packages it needs are here
  8  unpacked into plugins/.installing-<name>-<random>/
  9  its code imported, every route held to its permissions and to the platform's routes
 10  the platform's history, then its own, run and judged    (when a database is configured)
 11  renamed into plugins/<name>/ — a newer version replaces the old one in two renames
```

Any refusal removes the staging directory and unloads the module: the plugins directory is as it
was. Each refusal test asserts exactly that, not only the exception. Steps 9 and 10 are repeated
by the service every time it starts, so a plugin copied into the directory by hand is held to
the same rules — and tested that way, in `test_plugin_code.py`.

### Unpacking a hostile archive

A signature says who sent a package, not that it is safe to unpack — a build machine can be
compromised, a publisher can make a mistake. So a **signed** archive is still read as hostile,
and every entry is checked before one byte is written:

| Refused                                                         | Why                                                |
| --------------------------------------------------------------- | -------------------------------------------------- |
| `/abs`, `C:/x`, `a\b`, an empty, `.` or `..` segment            | could resolve outside the package directory        |
| a symbolic link                                                 | a link to `/etc`, then a file written through it   |
| a device, a FIFO, anything but a file or a directory            | not content                                        |
| an entry outside `manifest.toml`, `backend/`, `migrations/`, `ui/` | the format is closed                            |
| a name used twice, **in any letter case**                       | a case-insensitive disk writes the second over the first |
| an encrypted entry                                              | cannot be checked                                  |
| more than 4096 entries, or 256 MiB declared                     | a package, not a disk-filler                       |
| more than 256 MiB **actually inflated**                         | counted while written, not taken from the header   |

Then a second, independent line: `unpack` resolves every target and refuses one outside the
package directory, writes only into a directory it has just created, and opens every file for
exclusive creation, so nothing already on disk is followed or overwritten. A test proves the
second line on its own, by handing `unpack` a package that skipped the first.

## Loading an installed plugin's code

```
plugins/inventory/backend/__init__.py   ──imported as──▶   inventory        (top-level module)
plugins/map-editor/backend/__init__.py  ──imported as──▶   map_editor
```

`importlib.util.spec_from_file_location` with the backend directory as the package's only search
location. **Nothing is added to `sys.path`**: a path entry would make every file in the directory
importable under any name, which is exactly how a package shadows another. Inventory uses only
relative imports (R4's AC-11), so it does not care that it is `inventory` here and
`wavemaker.apps.inventory` when built in.

**Shadowing is refused** — at install, before unpacking, and again at load, before a line runs:

- `wavemaker` and anything starting with it — the platform;
- every standard library module (`json`, `os`, …);
- anything already imported, or importable from what is installed (`fastapi`, `sqlalchemy`,
  `mypy`).

A plugin's own earlier copy is not a clash: the loader marks every module it creates, and loading
again — an upgrade, or a second service in one process — drops the marked copy first.

**Mounting order.** Built-ins first, then installed plugins, each in name order. Starlette answers
with the first route that matches, so no plugin, whatever its name, can be put in front of a
built-in. Then each installed router is checked:

- every path under `/api/v1/<name>` or a declared prefix, compared **segment by segment**:
  `/api/v1/inventory-evil` is not under `/api/v1/inventory`, and a route parameter never matches
  a declared literal, so `/api/v1/admin/{anything}` cannot sit under `/api/v1/admin/items`;
- no (method, path) another app already answers — a manifest may declare `/api/v1/public/waves`,
  and content still owns it.

FastAPI 0.162 keeps an included router as one entry that resolves its routes when asked, so a
router's `routes` is not the list of paths it answers. Paths are read through
`fastapi.routing.iter_route_contexts`; a test hides a forged `/api/v1/public/status` inside a
sub-router and it is found.

**A plugin with no code is now refused.** R1 registered an installed plugin and gave it no routes,
because nothing put its code on the path; that is what this release changes. `/health`'s test
plugins now carry a router, and the test asserts their routes answer.

## Migrations: one history per app, judged by what it did

### The design: a version table per app

```
alembic_version                  the platform's history, unchanged — still one head
inventory_alembic_version        inventory's own history          (the app's prefix, so the app's)
achievements_alembic_version     another plugin's
wavemaker_app_object             what each app owns, kept by the runner
```

An app ships `migrations/`, ordinary Alembic revision files. The platform runs them with **its
own** `env.py` (`platform/plugins/history/env.py`) — an app ships revisions, not the code that
runs them — into `<prefix>alembic_version`.

**Why not an Alembic branch per app in the platform's history.** Every head is a row in the one
`alembic_version` table. Remove a plugin and its row names a revision whose file no longer
exists; Alembic then refuses to migrate *anything*, and one uninstalled plugin stops the platform
starting. Branch revision ids also share one namespace, so two plugins' `0001` collide, and every
plugin revision would have to name a platform revision as its parent. A table per app has none of
these: a history can come and go without the platform noticing, ids are scoped to one app, and
**nothing is added to the platform's `versions/`**, whose heads other work is extending in
parallel.

The platform's history always runs first, so an app may reference `project` and `player` with a
foreign key. It may not change them.

### Enforcement: the transaction is the check

PostgreSQL runs DDL inside a transaction. So:

```
  begin
    advisory lock                    two replicas never run one history at once
    snapshot the catalog             every object outside the system schemas, fingerprinted
    alembic upgrade heads            the app's revisions, with the network refused
    transaction id unchanged?        else: refused — it committed
    snapshot again, and judge
  commit only if every difference is the app's own;  otherwise rollback, naming each object
```

**The fingerprint** of every relation covers its columns, defaults, constraints, non-internal
triggers, policies, rules, owner, grants, comment, options and `relfilenode` — so `ALTER`,
`COMMENT`, `GRANT`, a trigger and `TRUNCATE` all show as a change. Functions and types are listed
and fingerprinted the same way. **Rows written** are counted from `pg_stat_xact_user_tables`, which
reports what the *current* transaction inserted, updated and deleted, so an `UPDATE project` shows
up although the schema did not change. And a list of objects no app may create, drop or change at
all: schemas, extensions, event triggers, roles and memberships, foreign data wrappers and
servers, publications, database settings, default privileges, languages, casts.

**The judgement** (`persistence/catalog.py`, a plain function over two snapshots):

- created: a table, view, sequence, type or function must carry the prefix; an index, or a
  sequence owned by a column, belongs to its table, so `pk_inventory_item` is inventory's because
  `inventory_item` is, and an index **on `player`** is refused;
- altered or dropped: only what the app owns;
- rows written: only into tables the app owns;
- cluster-wide objects: never.

**Ownership is recorded, not inferred from the name.** A plugin called `api` owns `api_*` — but
the platform's `api_key` existed before its history ran, and is not its. So the runner records
every object an app creates in `wavemaker_app_object`, and only recorded objects can be altered or
dropped later. The table is the runner's; an app writing it is refused like any other foreign
write (tested). It is created by the runner with `create table if not exists`, as Alembic creates
its own version table, rather than by a platform migration.

### Inventory, and 0005

`0005_inventory` is in the platform's history, cannot be edited, and runs on every database — so
every database has inventory's tables whether inventory is built in, installed, or absent. Moving
them out needs a revision in the platform's history, which is the maintainer's call while other
branches extend it.

Until then:

- inventory's own first revision, `apps/inventory/migrations/0001_inventory_tables.py`, creates the
  same tables with `if not exists`. On a database that ran 0005 it changes nothing; on one that
  never did, it builds them;
- the runner hands those three tables to inventory by name (`HANDED_OVER` in
  `plugins/migrations.py`) the first time inventory's history runs, so inventory owns them and its
  next revision may alter them;
- a test runs inventory's history on a database stopped at `0004m` and compares the result with
  0005's, column, constraint and index — so the two can never quietly come apart.

Built-in inventory runs its own history too, through the same runner. A built-in and an installed
copy are the same thing to the migrations, as they are to the loader.

## What is enforced, and what is not

In-process Python cannot truly sandbox code it imports. That is the design's step 3 — a plugin in
its own process, over the same ports — and not this release. Here is the honest line:

| Permission            | Enforced                                                                                      | Not enforced — and why                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Who published it**  | checksum and Ed25519 signature with a trusted key, before unpacking or import                 | —                                                                                                      |
| **tables = "own"**    | **in its migrations, completely:** every created, altered, dropped object and every row written, checked in the transaction and rolled back | **at request time:** the plugin's code shares the service's database session and can query any table. Only a separate role or a separate process stops that. Reads are never detected. |
|                       |                                                                                               | a migration that issues `COMMIT`: refused, but what ran before it stays (a test says so)               |
|                       |                                                                                               | another app's sequence values, large objects                                                           |
| **routes**            | every path at mount, segment by segment, plus no collision with another app                    | a route added later — to its router, or to `request.app` — is out of reach of a check at mount        |
| **module name**       | refused at install and at load                                                                | code that rebinds `sys.modules["wavemaker"]` once it runs                                              |
| **outbound_http**     | an audit hook refuses socket connect, name lookup and datagram send from a denied plugin's code: by the call stack while serving a request, and for everything while it is imported or migrated | a function handed to a thread pool (no plugin frame on the stack), a C library opening sockets beneath Python, a subprocess. A guard against accidents — an SDK that phones home, a library that fetches — not against an author who means it |
| **events**, **storage** | read and validated; carried on the manifest                                                  | not enforced: there is no event bus yet, and the blob store has no per-app quota                       |

Built-in apps ship with the platform and are reviewed with it, so their **routes** are not held to
a `[permissions]` table. Their migrations go through the same runner as an installed plugin's.

## What changed in earlier tests

- `/health`'s test plugins (`achievements`, `quests`) carry a router now, and the test
  asserts their routes answer. R1's "an installed plugin is registered and contributes no routes"
  is no longer true, and the test says what is.
- Nothing else. The service now mounts before it migrates — so a plugin refused for its routes or
  its module name has not changed the database — and every existing test passes unchanged.

## Still owed

- **Inventory's tables in the platform's history.** `0005_inventory` creates them everywhere.
  Handing them to inventory's own history for good needs a platform revision, and a decision about
  what happens to the tables on a service that does not install inventory. The maintainer's, with
  the parallel `0006`.
- **Per-plugin database roles.** The one change that would make `tables = "own"` true at request
  time inside this process: run each plugin's sessions as a role granted only its own tables. It
  needs the service's database user to create roles, which a self-hosted install may not grant.
- **Out of process** — the design's step 3, for plugins nobody has reviewed.
- **Uninstall.** Removing the directory stops the code; its tables, version table and ledger rows
  stay. A command that runs the history down, or deliberately does not, is not written.
- **`requires_plugins`**, from the design's manifest, is not read.
- **Events and storage** permissions are validated and carried, not enforced (no event bus, no
  per-app blob quota yet).
- **The `ui/` folder** is packaged and unpacked; serving it is R8's — done in its second half (`docs/platform/r8.md`).
- **A registry server**, when there are enough plugins to need searching. The install command
  stays the same.
