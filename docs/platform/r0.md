# R0 — the core boots and loads apps

The first release of [WaveMaker](../architecture/platform.md). It adds no game feature. It
answers one question: can this service start, find the apps on disk, and refuse the ones that
must not run?

## Acceptance criteria

|          | Criterion                                                                           | Where it is proved                          |
| -------- | ----------------------------------------------------------------------------------- | ------------------------------------------- |
| **AC-1** | The service boots and `/health` returns `status: ok` with the platform version      | `tests/integration/test_health.py`          |
| **AC-2** | With no plugins directory configured the service starts, with no apps               | `test_health.py`, `test_plugin_loader.py`   |
| **AC-3** | Every directory holding a `manifest.toml` is loaded, in name order                  | `test_plugin_loader.py`, `test_registry.py` |
| **AC-4** | Two apps claiming the same name stop the service starting, and both files are named | `test_registry.py`, `test_health.py`        |
| **AC-5** | An app needing a platform version this one is not is refused at startup             | `test_registry.py`, `test_health.py`        |
| **AC-6** | `/health` lists every loaded app with its version                                   | `test_health.py`                            |

Run one criterion on its own:

```bash
cd service && python -m pytest -q -k ac4
```

## What a manifest looks like

```toml
[plugin]
name = "inventory"
version = "1.0.0"
requires_platform = ">=0.1"     # optional: left out means "runs anywhere"
```

One plugin is one directory holding a `manifest.toml`. A directory without one is not a broken
plugin, it is not a plugin, and is skipped in silence.

## Decisions, and where they came from

Four of these are lifted from the Java plugin work on `feat/let-s-implement-next-version`, which
had already solved the same problems once. That branch is not merged — it stays as the reference
it was read as.

**Parsing is an adapter's job, never the kernel's.** The Java put descriptor reading in
`PluginConfiguration` and kept `PluginTypeRegistry` a plain holder, because Jackson and the
filesystem are banned from `engine-application`. The same split here: `kernel/` is plain Python
and `plugins/loader.py` owns TOML and the disk. It is not a convention — `lint-imports` fails the
build when the kernel reaches for a framework.

**An unset directory means "no plugins", not a path to guess.** Straight from
`PluginsProperties.isConfigured()`. Today's state is no plugins directory, and that must keep
starting the engine. A directory that _was_ set and is not there is a mistake, so it raises.

**A duplicate name fails startup, before the registry exists.** Also from the Java. Whichever
file won silently, one author's app would stop existing. The error names both files, because the
fix is to change one of them and nothing else can say which two collided.

**Refuse at build, not at request time.** `create_app` loads and registers while the application
object is being built, so a bad manifest stops the service instead of leaving it answering some
routes and failing others.

**A version range that will not parse is a refusal, not a shrug.** New here, and the reason is
the pattern this whole plan is built around: a typo like `requires_platform = "newer than 1.2"`
must not quietly become "runs anywhere" and load an app onto a platform it was never built for.
There is a test that fixes this.

**Apps are held in name order.** So that two services given the same plugins mount routes and run
migrations in the same sequence. Directory order is whatever the filesystem feels like, which
would make a startup difference impossible to reproduce.

## What R0 does not do

No database, no identity, no tenancy, no HTTP for apps — a manifest is read and remembered, and
nothing is mounted from it yet. Routers, migrations and permissions arrive with R1, when there is
a real app to mount.
