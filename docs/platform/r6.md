# R6 — leaderboards and progression

Scores, and how far a player has come. Two new apps, `leaderboard` and `progression`, and the
player-level routes R3 left owed: `listPlayers` and `getPlayer` with the platform's players,
`rewardPlayer` with progression.

## A leaderboard fed by clients is a leaderboard of what clients claimed

Said first, because everything else on a board depends on it. A player submits their own score
from the game, and this service cannot tell a real lap time from an invented one. No credential
design changes that: whatever the game can send, anybody who unpacked the game can send. So a
board shows what clients said they scored, nothing more. A game that needs better submits from
its own server, which is the only place a score can be checked against what happened.

That is why a player may submit a score but may not grant themselves currency or XP. A forged
score is cheating, and is visible and bounded: it is one row on one board. A forged grant is
minting. Submitting is a player route; granting and rewarding are editor routes, behind a
credential that never ships inside a game.

Where the answers differ from the generated document or from the Java, and why:

- **`deleteLeaderboard` answers 204**, as the Java did. The document says 200 because springdoc
  writes the default when an annotation says nothing; R2 and R7 made the same call.
- **`getLeaderboardPageAsAdmin` also accepts `cursor`.** The contract names only `limit`, and
  the Java served the first page and nothing else — while handing back a `nextCursor` nobody
  could use. Accepting an optional parameter breaks no generated client.
- **A score submitted to a board that is not there is 404.** The Java answered 422. The board
  is the path's resource, and every other route answers its absence with 404.
- **A cursor this service did not issue is 422.** The Java quietly served the first page. A
  client whose cursor was damaged and is sent back to the start sees every row twice, and has
  no way to tell; an error it can see is the kinder answer.
- **The curve's validation names the index the request sent.** See below.

## The guarantee, and no more than it

```
   board, descending            a walk, 3 per page          meanwhile
   ------------------           ------------------          ---------------------------
   900  P7                      page 1: 900 P7              P2 climbs 200 -> 950
   700  P4  \  a tie: P4 and    page 2: after (700, P1)     a newcomer arrives at 800
   700  P1  /  P1, broken by    ...
   500  P9     player id
   200  P2
```

A page asks for the rows after the last row of the previous page — after the *value*
`(score, player_id)`, not after a position. Rows written above that value do not shift the
rows below it, so a row whose score does not change is returned **exactly once** across the
walk. A row whose score changes moves: P2 above climbed past the walker and will not be seen,
which is what a live ranking is. Nothing here promises otherwise, and the contract does not
either.

The tie-break is not decoration. Scores tie constantly — everybody who finished the tutorial
has the same one — and a cursor over an order that is not total lands inside a tie and cannot
say which of the tied rows it has passed. With `player_id` as the last part of the key the
order is total, and the cursor exact. One index, `(project_id, board_id, score, player_id)`,
serves both directions, since a B-tree reads backwards as cheaply as forwards.

The rows of a page, the rank of its first row and the board's total come from one statement,
so they describe one moment. Ranks are positions in that total order, computed per read and
never stored.

**Proved concurrently.** Six writer threads, each with its own connection, raise movers'
scores and add new players above and below the walker, without pause, while a player walks a
board of 240 unchanged rows — five on every score, so page boundaries fall inside ties — seven
at a time over HTTP. The walker waits for a write to commit between every two pages, so the
writes are known to land inside the walk. Every unchanged row must appear exactly once, and the
keys returned must be strictly decreasing. Three rounds, in a database of the test's own.

**And checked by breaking it.** Both breaks were made, watched fail, and reverted:

| Change                                                   | What the tests said                                            |
| -------------------------------------------------------- | -------------------------------------------------------------- |
| Offset paging in place of the keyset                     | All three concurrent rounds: *an unchanged row was repeated*   |
| A keyset on `score` alone, without the tie-break         | All three concurrent rounds: *an unchanged row was skipped*; the tie test and the own-rank test failed too |

The same walk also runs with the writes put between pages by hand, where the outcome is
deterministic, so a failure there reproduces on every run.

### Players are paged the same way

`listPlayers` walks `(last_seen_at, id)` descending, through the same platform cursor helper
(`wavemaker.platform.paging`), with the same guarantee: a player not seen during the walk is
listed exactly once; one who starts a session moves to the front, which the walk has passed.

**A bug the Java had here:** its cursor carried `last_seen_at` as epoch *milliseconds*, while
PostgreSQL keeps microseconds. Of two players seen in one millisecond on either side of a page
boundary, the second compared against the truncated cursor as if it were newer, and was never
listed. The cursor here keeps the full timestamp with its zone. The test for it fails when the
cursor is truncated to milliseconds.

## Progression

The project's curve is data — stages with a cumulative `xpRequired` — and a player's stage is
derived from their XP and the curve on every read. There is no stored stage to go stale, so
editing the curve moves every player at once, with nothing to migrate.

**The curve is replaced whole**, because stages only mean something relative to each other.
Every problem is reported in one 422, as a list, each problem led by its pointer. The Java
sorted the stages and then reported the index in its *sorted* copy, so an author who sent them
out of order was pointed at the wrong row. The pointers here are the indices the request sent.

**Two saves at once are not a 500.** Replacing is a delete and an insert, and under read
committed two of those do not serialise: the second delete cannot see the first one's new rows,
and its insert collides with them. A transaction-scoped advisory lock keyed by the project makes
the second wait and then replace the curve whole. With the lock removed, 19 of 20 concurrent
saves failed with a unique violation; with it, all 20 succeed and the result is one of the
curves sent, not a blend.

**Awarding XP is one upsert**, the wallet's pattern: twenty concurrent first awards of one XP
make twenty, and the totals they report are 1 to 20, each once.

### A reward spans two apps, through a port

`rewardPlayer` awards currencies and XP in one transaction: one refused grant rolls back the
whole reward, XP included. XP is progression's and currency is the economy's, and apps may not
import each other. So the platform owns a small port, `wavemaker.platform.currency`:

```
  progression                   platform                        economy
  -----------                   --------                        -------
  reward():                     CurrencyLedger (Protocol)       PostgresLedger
    add XP          --session-> credit(session, project,  <---  the wallet's grant upsert,
    for each grant:               player, currency, amount)       on the caller's session
      ledger.credit                 must not commit               provided when loaded
    commit / rollback           provide(ledger) / provided()
```

The ledger credits inside the caller's session and never commits, so the reward stays one
transaction. A test stands a ledger in that writes a visible row and refuses one currency; a
reward of 100 XP and two grants whose second is refused leaves the player with no XP and no
mark. Committing after the XP, deliberately, makes that test fail.

**The economy provides the ledger.** `PostgresLedger` runs the same single-statement upsert as
a wallet grant, project filter included, on the session it is handed, and never commits. What
a request can cause — a balance that would not fit, a player who is not in this project, a code
or amount the grant route would refuse — comes back as `CurrencyRefused`, which the reward
reports at `/grants/{index}`. Without the economy's own refusals mapped there, an overflowing
balance would have reached progression as a numeric error and been reported at `/xp`. The
tests run through the real service: a reward pays into the same wallet a grant does; a refusal
by the economy rolls back the XP and every grant before it; twenty concurrent rewards of one
coin and one XP end at twenty of each.

**When nothing provides a ledger, a reward that names a currency is refused whole**, with 422
at `/grants`, before anything is written. In this service that means the economy app is not
loaded. Awarding the XP and dropping the coins would be the partial reward this route exists to
prevent. A reward of XP alone works either way.

## Decisions

**`listPlayers` and `getPlayer` are the platform's**, beside the player table and `/player/me`,
because players are. **`rewardPlayer` is progression's**: it is the XP app's write, and the
currency half crosses the wall through the port rather than through an import.

**Every per-player key leads with the project.** The economy's key is `(player_id, currency)`,
which let an upsert from one project conflict with another project's row, and needed an extra
`where` to stop it adding to it. `leaderboard_entry` and `progression_xp` are keyed with
`project_id` in front, so a conflict across projects cannot happen at all; the composite
foreign key to `player (id, project_id)` then refuses a player from elsewhere.

**Writes are single statements, decided by the database.** Saving a board is an upsert (the
Java updated, found nothing, inserted, and the second of two concurrent creators failed).
Submitting a score is an upsert whose `do update ... where` compares in the board's direction,
so a better score is never lost to a worse one arriving with it. The Java did update-then-insert
and caught the insert's unique violation, which in PostgreSQL leaves the transaction aborted:
the read it made next, to say what the board held, could only fail. An equal score is not
better, so the time a player first reached it is kept.

**Negative scores are allowed**, from the smallest to the largest bigint: golf, a time under
par, a net result. `true` is not a score of one.

**No in-memory adapters.** As in R3: the rules these apps exist for are PostgreSQL's to keep.

## Migration

`0006_leaderboards_progression` sits on `0004m`. R4 (inventory) is being written in parallel as
`0005`, also on `0004m`, so the history will fork into two heads again; the maintainer joins
them with a merge revision that changes nothing in the database, as `0004m` did. Neither file
should be edited to sit on the other.

```
  leaderboard_board   (project_id, board_id) PK · name · descending · timestamps
  leaderboard_entry   (project_id, board_id, player_id) PK · score · updated_at
                      -> leaderboard_board on delete cascade
                      -> player (id, project_id) on delete cascade
  progression_stage   (project_id, stage) PK · xp_required unique per project · label
  progression_xp      (project_id, player_id) PK · xp >= 0
                      -> player (id, project_id) on delete cascade
```

- The skeleton test and both `/health` tests list the built-in `leaderboard` and `progression`.
- `/health`'s test plugin called `leaderboard` is now `achievements`, since an installed plugin
  may not take a built-in app's name.
- R3's "no player route takes a player id" read *no `{` under `/api/v1/player`*. The contract

  that parameter and nothing else, so a player id under `/api/v1/player` still fails it.
