# R9 — remove the Java

The Java engine (`engine/`, Maven, Spring) stayed in this repository as the reference the Python
rewrite was checked against. R9 deletes it, and only after three things were true: the v1
contract is proved against the Python, CI builds no Java, and the Quickstart deploys the Python
service with PostgreSQL and real volumes. The deletion is the last commit, so the history shows
the proof before the removal.

## Acceptance criteria

|          | Criterion                                                                                | Proved by                                         |
| -------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **AC-1** | Every operation in `docs/api/openapi-v1.json` is served by the Python at its method and path | `service/tests/integration/test_frozen_contract.py` |
| **AC-2** | No removed property, no removed enum value, no optional request field made required      | the same file, by one walk through every operation |
| **AC-3** | CI builds no Java: no Maven, no JDK, no Java CodeQL                                       | `.github/workflows/*.yml`                         |
| **AC-4** | The Quickstart builds the service image and deploys it with PostgreSQL and named volumes | the `Quickstart` job                              |
| **AC-5** | An uploaded file survives the service container being replaced                           | the `Quickstart` job                              |
| **AC-6** | The editor's Playwright journeys pass against the Python: the journey, and R8's plugin screen | the `Quickstart` job, `editor/e2e/journey.spec.ts`, `editor/e2e/plugin-ui.spec.ts` |
| **AC-7** | `deploy/.env.example` names every `WAVEMAKER_*` setting the service reads, and no Java one | `service/tests/unit/test_configuration_is_documented.py` |
| **AC-8** | The Java is gone: `engine/`, `pom.xml`, `mvnw*`, `.mvn/`, its Dockerfiles and its docs    | the last commit                                   |

## The contract proof

The Java's `FrozenContractTest` compared two generated OpenAPI documents. That cannot be ported
as it stood: the Python builds most bodies by hand, so stored bytes go out untouched and every
field is spelled the way the contract spells it, and FastAPI's own document therefore names only
2 schemas where the frozen one has 46. Comparing the two would prove nothing either way. So
`test_frozen_contract.py` checks the same promise against what the service actually does:

```
 docs/api/openapi-v1.json  (70 operations, 46 schemas, frozen at 1.0.0)
          │
          ├─▶ 1. routing   each operation's request is sent through the service's own router;
          │                the route that answers must have that method and that path shape,
          │                and the contract's operation id if the route sets one
          │
          ├─▶ 2. the walk  one real service on a real PostgreSQL; every operation is called
          │                at the contract's path, in an order that gives each one something
          │                to read
          │                  request body  = exactly the properties its frozen schema lists
          │                  response body ⊇ every property its frozen schema lists, typed
          │                  If-None-Match declared → the ETag it sent must buy a 304
          │                at the end: called == all 70 operations, met == all 46 schemas
          │
          └─▶ 3. optional  fields the Java accepted missing are sent missing, and accepted
```

The last assertion of the walk is what makes it a proof of the whole document rather than of the
parts somebody remembered to check: an operation or schema in the frozen file that the walk does
not reach fails the test by name. Removing a field from a response was tried on purpose
(`WaveSummary.updatedAt`), and the walk failed with `WaveSummary lost ['updatedAt']`.

Enums and requiredness, the Java test's last two rules, are stated as their own tests. The frozen
document declares no enums, so there is no value to lose; the walk checks any it meets, and a
baseline that adds one starts being checked without a change. Only three request properties are
required in it — `TokenRequest.email` and `.password`, `RefreshRequest.refreshToken`,
`ApiKeyRequest.name` — and the walk sends every request with exactly its schema's properties, and
with fewer wherever the Java accepted fewer: a level with no description, an item with no sprite
or attributes, a board with no direction, a mix track with no gain, a reward of only XP or only
currency.

The per-app contract tests from R2 to R7 stay. They pin each app's bodies to exact field sets;
this file is the one that cannot miss an operation.

### What the walk found

| Operation                                                    | Was                                   | Now                          |
| ------------------------------------------------------------ | ------------------------------------- | ---------------------------- |
| `getAppConfig`, `replaceAppConfig`, `getPublicAppConfig`     | not served: no release carried them   | served by the content app    |
| `nextWaveOrder`                                              | answered `{"order": n}`               | answers `n`, as typed        |

**Application configuration** is the settings document a game client fetches on every launch.
It was in the Java from `v0.2.0` and in the frozen contract, and no release from R1 to R7 named
it, so it would have been deleted with the Java. It is now part of the content app — migration
`0007`, the same verbatim-text-plus-generated-`jsonb` storage as a wave, `{}` for a project never
configured, editors and administrators only on the admin side, anonymous with ETag and 304 on the
public side — with the Java's `AppConfigIntegrationTest` and its authorisation rows carried over
in `test_app_config_api.py`.

**`nextWaveOrder`** is typed `integer` by the contract and the Java returned a bare integer. R2
wrapped it in an object and pinned the wrapper in its own test. Nothing in this repository calls
the route, which is how it survived until a test read the response type out of the document.

### Found beside the walk

**`currentCaller`'s `kind`** was `access` on the Python, the token's internal kind, where the Java
answered `USER` for a signed-in account and the getting-started guide showed exactly that. The
contract types the field as a plain string, so no comparison of documents and no walk of shapes
can see it; it turned up while the guide was being rewritten against a running stack. It is now
`USER`, and the walk asserts the value. The Java's other value, `API_KEY`, has no counterpart:
here a key buys a player session and is never a caller of `/api/v1/me`.

### Not served

None. Every one of the 70 operations is served and answers in the walk.

### Differences that are not breaks

- **37 of the 70 routes leave FastAPI to generate their operation id** (`list_waves_api_v1_…`)
  rather than setting the contract's. Generated clients are built from the frozen document, not
  from the service's `/openapi.json`, so a client sees the contract's names either way. The
  other 33 set the contract's id, and the routing test holds any route that sets one to it.
- **19 routes name their path parameter for what it identifies** (`{wave_id}`, `{asset_id}`)
  where the contract says `{id}`. A client sends a value, never a name, so the URL is the same.
- **Status codes.** The frozen document lists `200` for every operation because springdoc wrote
  the default. The Java answered `201` on create and upload and `204` on delete, and so does the
  Python; the walk accepts any 2xx, as a client must.

## What changed in CI

`main` requires four checks by name: `Build and test`, `Secret scan`, `Quickstart` and `CodeQL`.
Each keeps its name.

| Check            | Before                                            | After                                                              |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| `Build and test` | JDK 21, `./mvnw verify`                           | Python 3.12: `lint-imports`, ruff, mypy, the whole pytest suite    |
| `Service`        | the Python suite                                  | removed; `Build and test` runs it                                  |
| `Secret scan`    | gitleaks                                          | unchanged                                                          |
| `Editor`         | typecheck, lint, test, verify:types, build        | unchanged                                                          |
| `Quickstart`     | the Java image, `/actuator/health`                | the service image, `/health`; see below                            |
| `CodeQL`         | `Analyze java-kotlin`, `Analyze actions`          | `Analyze python`, `Analyze actions`, both with `build-mode: none`  |
| Release          | Maven package, the Java image, a jar attached     | the Python checks, then `ghcr.io/<owner>/wavemaker`, no jar        |

The Quickstart, in order: bring the stack up from `deploy/.env.example` exactly as the README
says; wait for `/health`; check every built-in app loaded and `/openapi.json` is served; check
protected routes answer `401`; sign in as the seeded administrator; check the generated `jsonb`
columns of `wave` and `app_config`; author, publish, fetch anonymously, and revalidate the list
and the document to `304`; upload a clip, **recreate the service container**, and compare the
bytes; check the editor's login page and cookie flags; run the Playwright journey; run R8's
plugin-screen spec; round-trip the import CLI; refuse a wrong password.

**R8's plugin-screen spec** (`editor/e2e/plugin-ui.spec.ts`, from R8's second half) installs and
removes a plugin itself, and the service reads its plugins only when it starts, so the spec runs
and restarts a service of its own rather than the compose one. The step gives it a virtualenv with
the service installed, a PostgreSQL container of its own on port 5433, and an editor built from
source on port 3001, pointed at the `127.0.0.1:8000` the spec serves on. The spec lands with R8's
second half, so this branch has to sit on a `main` that has it before the `Quickstart` check can
pass; it was run locally against a merge of the two, and all four of its tests passed.

The volume check recreates the container rather than restarting it. `docker compose restart`
keeps the container and its own filesystem, so it would pass even if the bytes had never reached
the volume. A recreated container has nothing of the old one but what was mounted into it, and
the step also confirms the file is under the mounted path.

Every step was run locally against the stack before relying on CI: all passed, including the
three tests of the journey and the four of the plugin-screen spec.

## The deployment

```
  deploy/.env ──▶ docker compose ─┬─▶ postgres   (wavemaker-db volume)
                                  │
                                  ├─▶ service    deploy/Dockerfile.service, uid 1001, :8080
                                  │              migrates, then serves; /health
                                  │              wavemaker-blobs   → /var/lib/wavemaker/blobs
                                  │              wavemaker-plugins → /var/lib/wavemaker/plugins
                                  │
                                  └─▶ editor     LUDUS_ENGINE_URL=http://service:8080, :3000
```

- **One image, one process.** The service migrates the database as it starts, so two processes
  starting together would both try.
- **Installed in place.** The apps' manifests and migration histories are read from the package
  directory and are not modules a wheel would carry, so the image runs the source tree the tests
  run.
- **FFmpeg is opt-in** (`WAVEMAKER_WITH_FFMPEG=true` at build time, then
  `WAVEMAKER_MEDIA_FFMPEG_BINARY=/usr/bin/ffmpeg`), as the Java's separate image was.
- **`deploy/.env` is handed to the service as written.** The service reads an empty value as a
  value, so an optional setting is commented out, not blanked. Compose computes the database URL,
  refuses to start without a signing secret, and pins the blob and plugin directories to their
  volumes.
- **New volume names.** A Python service pointed at a Java database would fail its first
  migration, and quietly reusing the old volume would look like data loss with nothing to
  explain it.

## Not done here

- **Moving an existing Java install's data.** The Python schema is built by its own migrations
  from empty; nothing reads a Java database. An install that has content in the Java engine
  exports it (the waves through the API, `scripts/import-waves.mjs` to bring them back) or keeps
  running the last Java release. A migration tool is its own piece of work.
- **CodeQL for the editor.** Neither the Java CodeQL nor this one analysed `editor/`. Adding
  `javascript-typescript` is a one-line change to the matrix, left out here so that the first run
  of a new language's findings is not also the run that has to keep `CodeQL` green on this
  change.
- **`docs/api/openapi.json`** stays. It was the Java's generated snapshot and is byte-identical
  to `openapi-v1.json`; nothing regenerates it now, and a comment in the editor's content module names it.
  The frozen file is the one the tests read.
